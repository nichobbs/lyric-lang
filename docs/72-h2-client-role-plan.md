## 0. Summary

1. `H2Conn` is the right base. The frame codec, HPACK and most of the stream/flow-control machinery are already role-neutral. The server-only parts are a bounded, enumerable set of sites (section 1.3, 31 sites).
2. Recommendation: add a role to the existing FSM in `http_h2conn.l` (not a sibling module), keep every existing public server name and signature source-compatible, and add additive client API and client events. Put the role state in a new sub-record, because the JVM backend's record-arity limit (#6089, see section 1.2) is a hard constraint on `H2Connection`.
3. Build the transport driver once in pure Lyric over `Std.TcpHost` (`Std.HttpEngine.H2Client`), after adding client TLS with ALPN to the dotnet and JVM `tcp_host.l` kernels (native already has it).
4. Layer a pure-Lyric gRPC client on that driver, and a pure-Lyric JVM gRPC server on the existing dotnet server code (generalised to the portable `Std.Task` primitives). Keep `Grpc.Net.Client` and grpc-java only as independent interop fixtures in tests, then drop them from the shipping dependency set.
5. Total: roughly 9 slices, one L (the FSM client role plus its conformance matrix), several M, the rest S. Nothing in slice 1 to 3 changes server behaviour; the server's existing 82-test corpus plus the new loopback tests are the regression net.

Facts from the brief that I checked and confirmed: line numbers (even-id rejection L1287, `isIdleStreamId` L712-714, draining check L1323-1330, PUSH_PROMISE L1884-1886, rapid-reset state L375-381), `expectPreface` in `newFrameDecoderWithMaxSize` (http_h2frame.l L1190) and `connectionPreface()` (L498), and TLS+ALPN client only on native. One small correction: the draining check comment is at L1323 but the code is L1328-1330. Another useful fact not in the brief: `Std.Http` on native is HTTP/1.1 only by design (`_kernel_native/http_host.l` header, items 1: "HTTP/1.1 only, never h2", ALPN advertises only `http/1.1`), so an h2 `Std.Http` client on native is new capability, not a fix.

## 1. H2Conn design

### 1.1 Role flag on the existing FSM vs a sibling module

Decision: role flag (`H2Role = H2Server | H2Client`) on the existing `H2Connection`. Rationale:

- Roughly 70 percent of `http_h2conn.l` (about 1,700 of 2,470 lines) is role-neutral [V by reading]: SETTINGS apply (L871-981), PING (L1006), WINDOW_UPDATE (L1028-1090), DATA receive and flow control (L1131-1273), HEADERS+CONTINUATION assembly (L1431-1533), HPACK decode, `sendData`, `grant*Window`, `sendRstStream`, query surface. A sibling module would copy these and fork every future bug fix (the file already carries 20+ numbered hardening fixes: #6063, #6064, #6074, #6082, #6084-6090, #6562, #7231, #7251, #7265, #7269 ...). That is exactly the "bootstrap-grade duplication" CLAUDE.md prohibits.
- The server-specific logic is concentrated in five places: stream creation on first HEADERS (`beginNewStreamHeaders`), request validation (`malformedRequestReason`), the idle-id test (`isIdleStreamId`), the GOAWAY last-stream-id, and the preface/first-frame handling. All are cleanly gated by a role value.
- Against: a role flag adds branches to code that is security-sensitive (rapid reset, CONTINUATION flood). Mitigation: gate by role at the five sites only, and run the entire existing server corpus unchanged as the regression guard (slice 1 acceptance).

Rejected alternative: sibling `Std.HttpEngine.H2Client` FSM reusing only the frame and HPACK modules. It would be about 1,200 new lines duplicating flow control and CONTINUATION handling. Revisit only if the role branching proves unreadable in review.

### 1.2 Hard constraint: record arity on the JVM backend [V]

`H2ShutdownState`'s doc comment (L362-373) records that the self-hosted JVM backend under-computes `max_stack` for record constructors with about 15+ fields (#6089), which is why that sub-record exists. `H2Connection` currently has exactly 14 fields (`dec, hpackDec, hpackEnc, localSettings, remoteSettings, connSendWindow, connRecvWindow, streams, streamIndex, cont, lastPeerStreamId, expectClientSettings, fatal, shutdown`, L388-406). Adding role fields flat would reach 15 to 18 and break JVM `newClientConnection`.

Plan: introduce `ref record H2RoleState { role: H2Role; var nextLocalStreamId: Long; var highestPeerStreamId: Int; var expectPeerSettings: Bool; var peerGoAwayLastStreamId: Int }` (shipped in D797; `nextLocalStreamId` is a `Long` because the id after 2^31-1 does not fit `Int`) and MOVE `lastPeerStreamId` and `expectClientSettings` into it (net: 14 - 2 + 1 = 13 fields). Both moved fields are internal; the only external reader is the public query `lastPeerStreamId(conn)` (used by `_kernel/http_server.l` L1180 and tests L1696-1700 [V by grep]), whose signature is kept. Same discipline for `H2Stream` (L334-341, currently 6 fields): adding `headerPhase`, `requestMethod`, `responseStatus` gives 9, fine.

### 1.4 Event vocabulary (keep server API source-compatible)

Keep all existing cases and names untouched: `H2RequestHeaders`, `H2RequestData` are emitted only by a server-role connection, so existing consumers (`_kernel/http_server.l`, `_kernel/grpc_server.l`, the 82 tests) compile and behave identically. Union cases cannot be aliased, so a role-neutral rename would break source compatibility; reject it for now.

Add (additive):
- `H2ResponseHeaders(streamId, status: Int, headers: List[HeaderField], endStream: Bool)` for the final response header block (a Trailers-Only gRPC response arrives here with `endStream = true`).
- `H2InformationalHeaders(streamId, status, headers)` for 1xx (never ends the stream).
- `H2ResponseData(streamId, data, endStream, wireLength)` (same shape as `H2RequestData`; the `wireLength` rule at L260-265 applies).
- `H2ResponseTrailers(streamId, headers)` (always END_STREAM). gRPC `grpc-status` and `grpc-message` arrive here, or on `H2ResponseHeaders` with `endStream` for Trailers-Only.
- `H2StreamUnprocessed(streamId)` (GOAWAY above last-stream-id; retry-safe) and `H2StreamRefused` is already expressed by `H2PeerReset(streamId, H2RefusedStream)` (retry-safe by RFC 9113 8.7).
- Everything else already exists and is role-neutral: `H2SettingsReceived`, `H2SettingsAcknowledged`, `H2PingReceived`, `H2PingAcknowledged`, `H2WindowUpdated`, `H2PeerReset`, `H2GoAwayReceived`, `H2ConnError`, `H2StreamErr`, `H2NeedMore`.

Open question OQ-1 (section 6): add one trailers case, or fold trailers into `H2ResponseHeaders` with a flag as the server side does (the server reports trailers through `H2RequestHeaders` too, L256-259). Recommendation: a separate case for clarity, since a client must distinguish a Trailers-Only response from response trailers.

### 1.5 Stream-id allocation and the open-stream API

`openStream(conn, headers, endStream)`:
- Preconditions: not failed, `isH2RequestHeaderListSafe(headers)`.
- Shipped in D797 with the cases prefixed `Open...` (`OpenConnectionDraining`, `OpenStreamLimitReached`, `OpenStreamIdsExhausted`, `OpenHeaderEncodingFailed`; a union case name cannot repeat across unions in one package) plus `OpenConnectionFailed` and `OpenHeaderListTooLarge`.
- Errors (new union `H2OpenError`): `ConnectionDraining` (peer GOAWAY received or we sent one), `StreamLimitReached(active, limit)` (locally-initiated active streams >= peer's SETTINGS_MAX_CONCURRENT_STREAMS; the driver queues and retries on a stream-close event, RFC 9113 5.1.2 says the opening endpoint MUST NOT exceed the limit), `StreamIdsExhausted` (next id would exceed 2^31-1; driver opens a new connection), `HeaderEncodingFailed(HpackError)`.
- The id is `nextLocalStreamId` then `+= 2`. Count only streams we initiated for the concurrency limit (`countActiveStreams` L600-611 counts all; with push disabled they coincide).
- Monotone ordering is subtle with a multi-threaded driver: HPACK encoding order must equal wire order and ids must increase on the wire (RFC 9113 5.1.1). The FSM is single-writer (it is a mutable reference record), so the driver MUST serialise `openStream` + write under one lock (the dotnet server already does this with a monitor, `grpc_server.l` `writeLocked` L192). Document as a contract.
- `END_STREAM` on HEADERS when the request has no body (unary gRPC always has a body, but a generic client GET does not): handled by the `endStream` flag via the existing `markEndStreamSent` (H2SOpen -> H2SHalfClosedLocal).

### 1.6 Client preface and SETTINGS

`clientInitialBytes` described in item 3. The ACK of the server's SETTINGS is already automatic (L1000-1002). The client must not send request HEADERS before receiving anything (RFC 9113 3.4 allows sending immediately after the preface; do not wait, one round trip saved). Note HPACK: until the server's SETTINGS_HEADER_TABLE_SIZE arrives the encoder uses the RFC default 4096, which is what `newEncoder(4096, true)` assumes, so this is safe [V: L520, L944-947].

### 1.7 Response header validation (RFC 9113 8.1, 8.3.2, 8.2)

Checked in `malformedResponseReason` (new, item 13): :status present once, three digits, first; no request pseudo-headers; no uppercase or invalid field names; no connection-specific fields (`connection`, `keep-alive`, `proxy-connection`, `transfer-encoding`, `upgrade`); `te` not allowed; content-length syntax; 1xx handling; final status required before DATA (DATA before final HEADERS = stream error PROTOCOL_ERROR); trailers carry END_STREAM and no pseudo-headers; content-length vs bytes received enforced (L1252-1254 path). Status 100-199 other than 101 are informational and a final response must follow. A response violating these is a stream error PROTOCOL_ERROR (RFC 9113 8.1.1) and the client surfaces `H2StreamErr`; a driver maps it to gRPC `Internal` or `Unavailable` as appropriate (see 4.4).

### 1.8 Flow control for the client

Both directions already exist. Client specifics:
- Receive: the driver MUST replenish by `wireLength` (not `data.length`) as the application consumes bytes (L260-265). Large initial connection window: the client should emit an initial connection-level WINDOW_UPDATE (for example to 1 MiB) with its SETTINGS, otherwise a 64 KiB connection window throttles server-streaming gRPC. `grantConnectionWindow` has `requires: increment <= h2MaxWindow() - connRecvWindow` (L2395), satisfied.
- Send: `sendData` returns `WindowExceeded` and the driver parks the call until `H2WindowUpdated` (the dotnet server driver currently polls with a 30 s limit, D287 item 3, `sendWindowWaitMs`). For the client prefer an event-driven wakeup (condition on the monitor) rather than polling; this is a driver concern.

### 1.9 GOAWAY, last-stream-id, PING, RST_STREAM, connection errors

- Peer GOAWAY: item 20. After it the connection is "draining": existing streams at or below last-stream-id continue; the pool must stop routing new calls to it. ERROR codes: `NO_ERROR` is graceful; others are surfaced to in-flight calls as UNAVAILABLE.
- Our GOAWAY (graceful pool close): `sendGoAway` with last-stream-id 0 (item 19). Then keep reading until streams finish, then close.
- PING: auto-ACK exists. Keepalive (RFC 9113 6.7) is a driver timer: send `sendPing` on an idle interval; if no `H2PingAcknowledged` within the timeout, close the connection and fail in-flight calls UNAVAILABLE. Keepalive-abuse limits on servers (grpc-java closes connections that ping too fast) must be configurable and conservative by default (open question OQ-5).
- RST_STREAM: `sendRstStream` for CANCEL (call cancelled, deadline passed). Received RST_STREAM on a stream we opened: `H2PeerReset`; `H2RefusedStream` is safe to retry.
- Connection errors: `connFail` appends GOAWAY and poisons; the driver fails every in-flight call UNAVAILABLE with the message and closes the socket.
- Frame-size and ENHANCE_YOUR_CALM guards (CONTINUATION flood `maxContinuationFrames` L444, header list size budgets L1470) apply unchanged and protect the client from a malicious server.

### 1.10 Size estimate for the FSM work

About +450 to +600 lines in `http_h2conn.l` (new constructors, `openStream`, response validators, response/trailer handling, GOAWAY client semantics, role gating) and +800 to +1,100 lines of tests. Slice size L, mainly because of the conformance matrix (section 2).

   - handshake, SETTINGS ack both ways, ordering rules (first server frame must be SETTINGS);

3. Negative matrix (hand-built malicious server bytes into the client): see 2.3.

### 2.5 Fuzz and property tests (slice 9, also run in every earlier slice for the new code)

### 3.5 The driver module `Std.HttpEngine.H2Client` (slice 5)

New `lyric-stdlib/std/http_h2client.l` (about 700 to 900 lines [A]), pure Lyric over `Std.TcpHost` + `Std.Task`, no extern, so one implementation serves all three targets (the docs/61 decision 6/8 intent for the engine). Shape:

- `H2ClientConnection` (ref record): owns the `Conn`, the `H2Connection`, a per-stream mailbox (queue of response events for the caller), a write lock, a reader task, keepalive state, and status (open, draining, closed).
- `connect(target: H2Target, opts): Result[H2ClientConnection, H2ConnectError]` where `H2Target` is `Plain(host, port)` or `Tls(host, port, trust, identity, minVersion)`; on TLS require `hostAlpn == "h2"`, else `Err(AlpnNotH2)` (no silent downgrade for gRPC; a general HTTP client can choose to fall back to HTTP/1.1 itself).
- `startCall(conn, headers, endStream): Result[CallHandle, ...]`, `sendBody(call, bytes, endStream)`, `nextEvent(call, timeoutMs)`, `cancel(call)`, `close(conn)`. Response bytes are credited back to the windows as `nextEvent` hands them to the caller (backpressure by not reading from the mailbox is bounded by the receive window, so a slow consumer cannot cause unbounded memory).
- Reader task: loop `hostRead(conn, 65536)` -> `feed` under the lock -> write `outbound` -> dispatch events to mailboxes -> wake blocked senders on `H2WindowUpdated`/stream close.
- Write coordination: exactly one lock covers FSM mutation and socket writes (the FSM is a mutable reference; `feed`, `openStream`, `sendData` all mutate it). The server driver does this with a raw .NET monitor (`grpc_server.l` L46-51 `monitorEnter/Exit` externs, dotnet-only [V]). The portable equivalent should be a Lyric `protected type` (Ada-style, used by `Std.Task.Scope` itself, task.l header [V], and shipped on native in N3.4/D-N-017 [V from CLAUDE.md]) or a `Std.Task` lock if one exists [A: confirm a portable mutex+condition on all three targets; `Std.Task` has native twins per target under `_kernel/`, `_kernel_jvm/`, `_kernel_native/task.l` [V by ls]]. Do NOT write the write path while holding the lock across a blocking `hostWrite` for large frames without a bounded I/O deadline (a stalled peer would freeze every call on the connection); use `hostSetIoTimeout`/bounded writes and treat a write timeout as connection failure.

### 3.6 Threads and async per target

- dotnet [V]: the existing server uses one `Task.Run` per call plus one reader task, blocking `hostRead`, and a monitor. Lyric's `spawn` on dotnet is "degenerate-synchronous" in the MSIL path (CLAUDE.md async_spawn description [V]), so a reader loop started with `spawn` would run inline and block the caller; do not use bare `spawn` for the reader on dotnet. Use the real task primitive in `Std.Task` (the BCL-task-backed `task.l`), or a small extern `Task.Run` in `_kernel/` as the server driver does (the CLAUDE.md rule is externs only in `_kernel/`; the server's `extern type Task` in `lyric-grpc/src/_kernel/net/` is acceptable there since it is a kernel dir, but a stdlib module must use `std/_kernel/task.l`).
- JVM [V from D611]: virtual threads; blocking reads are fine; a write timeout is implemented by an abandoned virtual thread, which has a cost per write (D611 item 3). Prefer to set the I/O timeout once and avoid per-frame timer churn in the driver.
- native [V]: pthreads via the kernel; blocking sockets; bounded variants exist and should be used for deadlines (D605). The reader thread must be wakeable for close and cancellation: use `WakePipe` (`hostWakePipeNew/Signal`, native-only) so `close` interrupts a blocked read. On dotnet/JVM the equivalent is closing the socket from another thread, which makes the blocked read fail (document the semantics and test it on all three).
- Needed API parity to avoid `@cfg` branches in the driver: expose a portable `hostReadDeadline(conn, maxBytes, deadlineNanos)` (dotnet: `ReadTimeout`/`CancellationToken`; JVM: `setSoTimeout` per read; native: `hostReadBounded` with `-1` wake fd) so the driver can bound reads for deadlines and keepalive without knowing the target. This is the same "parity" work D611 started for connect; propose it as slice 4b (S/M). The alternative (use `hostSetIoTimeout` as the only knob) is simpler but cannot express "deadline for the whole call" except by the driver's own timer thread closing the connection or sending RST_STREAM.

### 3.7 Deadlines, bounded I/O

- Per-call deadline (gRPC `grpc-timeout`, HTTP request timeout) is enforced by the DRIVER, not the socket: a monotonic deadline per call checked by the reader when it wakes (idle timeout tick, say every 50 to 100 ms or via a timed condition wait on the mailbox), and on expiry the driver sends `RST_STREAM(CANCEL)` and delivers `DeadlineExceeded`. The connection stays up for other calls. Socket-level timeout is only the connection idle/keepalive guard.
- Connection setup deadline: `hostConnect(..., connectTimeoutMs)` (D611) plus a TLS handshake bound (`hostSetIoTimeout` before the upgrade on dotnet/JVM; native has `hostUpgradeClientTlsBounded`).
- Write deadline: see 3.5.
- D605 (native request limits) is the model: the whole send is bounded by one absolute deadline and cancellable from another thread; mirror its outcome mapping (timeout vs cancelled vs failure distinguishable) in the driver's error union, because gRPC needs to distinguish `DeadlineExceeded` (maybe applied) from `Unavailable` (never sent).

### 3.8 Pooling, multiplexing, idle handling (slice 6)

- Multiplexing is inherent: one `H2ClientConnection` carries up to `min(peer MAX_CONCURRENT_STREAMS, configured)` concurrent calls. Calls beyond the limit wait on a condition and are admitted as streams close (fairness: FIFO).
- Pool keyed by authority + TLS identity: reuse an open, non-draining connection with free stream slots; open another connection when all slots are busy only if configured (`maxConnectionsPerHost`, default 1 for gRPC channels, matches grpc-java's default one connection per channel).
- Draining (peer GOAWAY) or failed connections are removed; in-flight calls complete or fail per 1.9; new calls transparently open a replacement.
- Idle: close after `idleTimeoutMs` with no active calls (send our GOAWAY first); keepalive PING only while calls are active, or with `keepAliveWithoutCalls` opt-in, defaults conservative.
- Transparent retry of `H2StreamUnprocessed` and `H2RefusedStream` calls exactly once on a new connection (RFC 9113 8.7; gRPC "transparent retry"). Never retry a call that may have been processed.
- Reconnect backoff for channels: exponential with jitter, separate from per-call retry policy (retries/hedging are out of scope for v1).
- `Std.Http` integration (native h2 client, slice 7): `_kernel_native/http_host.l` currently advertises only `http/1.1` and uses a hand-rolled HTTP/1.1 client; add ALPN `h2,http/1.1` and route h2 connections through `Std.HttpEngine.H2Client`, honouring `HttpVersion` semantics (docs/61 section 5.1, `withHttpVersion`) and existing D605 token/deadline behaviour. Dotnet and JVM `Std.Http` already use `HttpClient`/`java.net.http` which speak h2, so this slice is native only.

### 4.2 Unary and server-streaming client on `H2Client` (slice 6)

New portable package `Grpc.Client` (pure Lyric, in `lyric-grpc/src/client_h2.l`, about 500 to 700 lines [A]) used by BOTH targets and (later) native; kernels shrink to nothing.

- Request: `:method POST`, `:scheme http|https`, `:path /Service/Method`, `:authority`, `content-type application/grpc` (also accept `+proto`/`+json` suffixes on response), `te trailers`, `user-agent`, `grpc-accept-encoding identity,gzip`, `grpc-timeout` if a deadline is set, optional `grpc-encoding gzip`, then user metadata (validated with the existing `isValidMetadataKey/Value`, `-bin` keys base64 per the gRPC HTTP/2 spec).
- Message framing: 1-byte compressed flag + 4-byte big-endian length + payload; the server driver already has `frameMessage` (grpc_server.l L131) and `singleMessageLength` (L147): move both into a shared `Grpc.Wire` package used by client and server (also retires duplication). Reader reassembles messages across DATA frame boundaries (a message may span frames; several messages may share a frame) and enforces `maxReceiveMessageBytes` (default 4 MiB, mirrors grpc-java) with `ResourceExhausted`.
- `grpc-timeout`: encode the remaining deadline as an integer with unit (H,M,S,m,u,n; max 8 digits) rounding up; also arm the local deadline per 3.7 so client and server agree; on expiry cancel the stream and report `DeadlineExceeded`.
- Response: check `:status` first. Per the gRPC over HTTP/2 spec a non-200 HTTP status maps to a gRPC status (400 Internal, 401 Unauthenticated, 403 PermissionDenied, 404 Unimplemented, 429/502/503/504 Unavailable, other Unknown) when no `grpc-status` is present. Then `content-type` must start with `application/grpc` else `Unknown/Internal` with the HTTP status in the message. Read messages until trailers; take `grpc-status` (int; invalid/missing = `Unknown` "server closed without grpc-status" or `Internal`), `grpc-message` (percent-decode with the existing `decodeGrpcMessage`), `grpc-status-details-bin` ignored in v1 (open question OQ-6). Trailers-Only: `H2ResponseHeaders` with `endStream=true` carrying `grpc-status`: treat the headers as trailers.
- Stream end without trailers (RST_STREAM or connection loss) maps: `REFUSED_STREAM`/GOAWAY-unprocessed -> `Unavailable` (retry-safe); `CANCEL` -> `Cancelled`; `ENHANCE_YOUR_CALM`/`INADEQUATE_SECURITY` per spec table (RFC-to-gRPC mapping: PROTOCOL_ERROR/INTERNAL_ERROR/FLOW_CONTROL_ERROR/SETTINGS_TIMEOUT/COMPRESSION_ERROR/FRAME_SIZE_ERROR -> Internal; STREAM_CLOSED -> Internal; NO_ERROR with no status -> Internal; ENHANCE_YOUR_CALM -> ResourceExhausted; INADEQUATE_SECURITY -> PermissionDenied; connection failures -> Unavailable).
- Status mapping: the existing `GrpcStatus` and 17 codes already match; reuse unchanged. Existing aspects (`RequiresGrpcAuth`, `GrpcRateLimit`, `GrpcCircuitBreaker`) are transport-neutral [A: confirm they only touch `GrpcStatus` and handler metadata; they live in `aspects.l`, not read in detail] and need no change.
- Compression: `grpc-encoding: gzip` via `Std.Zip`. `Std.Zip` has `inflate(data, maxOutput)` (L512, bounded output, good for decompression-bomb safety), `deflate(data)` (L621) and `crc32` (L121) but had no gzip container (RFC 1952 header 10 bytes + deflate + CRC32 + ISIZE). Slice 3 (D798, shipped) added `Std.Zip.gzipEncode(data)` and `Std.Zip.gzipDecode(data, maxOutput)` (multi-member, optional header fields, total output cap, trailing bytes refused) with gzip(1)/Python vectors. `deflate` does compress (LZ77 + one fixed-Huffman block, stored fallback): within about 20 to 25 percent of `gzip -6` on prose and source, 1.7 times larger on very repetitive data (D798 has the table). Client sends uncompressed by default and advertises `grpc-accept-encoding: identity,gzip`; decodes gzip responses; per-call opt-in `withCompression(gzip)` for requests. Server side compression is currently out of scope (D287 item 6); add decode on request and optional encode on response in the same slice.
- Lyric-proto interop: payloads stay raw `slice[Byte]` (D068/D281); no change.

### 4.3 Client streaming and bidirectional streaming (decision)

Recommendation: ship unary + server streaming first (parity with today's API), then client streaming and bidirectional as a follow-up slice on the same driver, because the FSM and driver already support half-duplex and full-duplex (HEADERS then many DATA each way is native to h2). The blocker is API shape, not transport: the current `GrpcStream` is a pull iterator (`nextMessage`). Proposed surface for slice 8b: `openClientStream(channel, service, method, options): Result[GrpcClientCall, String]` with `send(call, bytes): Result[Unit, GrpcStatus]` (blocks on flow control, returns `Err` when the server closed), `halfClose(call)`, `receive(call): Result[Option[bytes], GrpcStatus]`, `cancel(call)`; unary-with-streaming-request is the same type with a single `receive`. Server side adds `ClientStreaming(handle: (recv: () -> Option[bytes], meta) -> Result[bytes,GrpcStatus])` and `Bidi(...)` to `GrpcHandler`. Must interplay with docs/37's "async streaming model (forward-looking)" and docs/68 structured tasks (a bidi API wants `Task` scoping); note this dependency, and do not block the unary/server-streaming slices on it. Decision requested in OQ-4.

### 4.4 Pure-Lyric JVM gRPC server replacing grpc-java's (slice 8)

`grpc_server.l` (813 lines) is dotnet-specific only through three externs: `Task.Run`, `Monitor.Enter/Exit` (L37-51) [V]. Everything else is H2Conn + `Std.TcpHost` + Std primitives. Plan: move the server into a portable package (`Grpc.Server.H2`), replace the three externs with the portable `Std.Task` / protected-type lock chosen in 3.5, keep `Grpc.startHandleAt/serverPort/stop/trackedConnections` semantics identical (including the `drainTimeoutMs` behaviour, 4 MiB request limit, `maxConnectionIdleMs`, Internal-without-detail on handler panic). Then the JVM kernel's grpc-java server (the `JServer`/`JNettyServerBuilder` types at jvm/grpc_kernel.l L358-362) is deleted and the JVM server tests run against the pure-Lyric server, with grpc-java kept as a CLIENT in tests only (independent peer). Risks: virtual threads and `synchronized`-pinning on JVM; handler panics must not kill the server (D287 item 2: catch at the task boundary; JVM has `panic_guard_host.l` in `_kernel` for exactly this [V by ls, A: usage]). TLS for the server (`hostAcceptTls`) is available on all three targets, so adding `startHandleTlsAt` is cheap and removes D287's "TLS out of scope" caveat (slice 8c, S).

### 4.5 Migration plan for the existing API and tests

- Public API: unchanged signatures for `openChannel`, `callUnary`, `openServerStream`, `nextMessage`, `closeStream`, `closeChannel`, `withTimeout`, `withMetadata`, server API. `GrpcChannel` and `GrpcStream` are already registry-key handles (opaque types holding an Int, types.l L120-160 [V]), which makes swapping the implementation behind them trivial.
- Address forms: today `openChannel("https://collector:4317")` is URL-ish. Keep: scheme `http://` = h2c prior knowledge, `https://` = TLS+ALPN h2. ## 6. Open questions needing a decision

- OQ-1 Event naming: separate `H2ResponseTrailers` case (recommended) vs flagging on `H2ResponseHeaders`; and whether to ever introduce role-neutral aliases (`H2Headers`, `H2Data`) with a deprecation window for the server cases (recommended: no, not in this epic).
- OQ-2 Role flag vs sibling module: recommended role flag (section 1.1). Decide before slice 1 starts because it determines the diff shape and review cost.
- OQ-3 Insecure TLS mode (`withInsecureSkipVerify` + `LYRIC_TLS_ALLOW_INSECURE`, docs/61 section 4) for the dotnet and JVM client kernels: the callback-free constraint (#5947) may make true "no verification" impossible; allow a documented unsupported result (`TlsConfigInvalid`) on those targets, or find a mechanism (spike in slice 4)? Production-readiness rules say a tracked, dated issue rather than a silent skip.
- OQ-4 Client and bidirectional streaming scope for this epic (recommended: slice 9, after unary/server-streaming), and the API shape (blocking `send`/`receive` handle vs `Std.Task`-based). Interaction with docs/37 and docs/68.
- OQ-5 Keepalive defaults and server `GOAWAY too_many_pings` compatibility (grpc-java: server permits pings at most every 5 min without calls by default; Go: similar). Default recommendation: no keepalive unless configured; keepalive-with-active-calls only, interval >= 60 s.
- OQ-6 `grpc-status-details-bin` (`google.rpc.Status`) and `grpc-web`: out of scope for v1; confirm.
- OQ-7 Concurrency primitive: which portable lock+condition is the contract for drivers (`protected type`, `Std.Task`)? Needs a spike to confirm it works with reader tasks on dotnet (non-synchronous), JVM, native before slice 5. Also whether the shared FSM lock should be coarse (one per connection, as in D287) or finer.
- OQ-8 Where should `TlsClientTrust` live (`Std.Tls` vs duplicated per kernel)? It is declared only in the native kernel today (L249).
- OQ-9 Default connection model for gRPC channels: one connection per channel (grpc-java default) vs pool of N. Recommended: 1, configurable.
- OQ-10 `Std.Http` on dotnet/JVM keeps using `HttpClient`/`java.net.http`; should it eventually switch to the pure-Lyric engine for uniform behaviour? Out of scope here, but it affects whether `H2Client` gets a general HTTP request/response API (`Std.HttpEngine.H2Client.requestResponse(...)`) in slice 7 or stays gRPC-oriented.
- OQ-11 Decision ids and docs: one decision entry for the H2Conn client role (slices 1-2), one for TLS client kernels (4), one for the driver and gRPC migration (5-10), superseding parts of D287 (items 3, 4, 6); and whether docs/61 gets a new section 6.5 "client role" or a new doc number.
- OQ-12 Maintaining grpc-java/Grpc.Net as interop fixtures: acceptable in CI as a separate interop project (recommended), versus replacing them with a Go or nghttp2-based server to keep the repo free of Java/NuGet SDKs entirely (fits docs/71 direction but loses gRPC-specific independent validation).
