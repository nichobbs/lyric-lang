# D787 - `Ws.startServer` on the JVM is the pure-Lyric RFC 6455 server over `Std.TcpHost` (docs/73 slice S7a)

**Status:** accepted. Extends D621 (S1, `Std.TcpHost` fit for a server) and D780 (the baseline and the B7 gate); supersedes nothing. The plan numbered this slice's decision D618; that id was taken, so S7a takes the next free one.

## Context

`Ws.startServer` ran the pure-Lyric RFC 6455 server (`Ws.Kernel.Net`, over `Std.TcpHost`) on dotnet and native and an Undertow server (`Ws.Kernel.Jvm`, 921 lines, 35 extern types) on the JVM. The Undertow kernel did not reassemble fragmented messages, sent no keepalive pings, decoded text leniently, and was the only user of the `io.undertow` coordinate in `Ws.startServer`'s path. Since D611 and D621 `Std.TcpHost` is a real server transport on the JVM, so the shared kernel can run there unchanged.

## Decision

1. **One kernel for `startServer` on every target.** `Ws.Kernel.Net` (`_kernel/net/ws_kernel.l`) is compiled on dotnet, the JVM and native. Its target-specific primitives are three twins in one package: `_kernel/net/ws_prims.l` (dotnet), `_kernel/native/ws_prims.l`, and the new `_kernel/jvm/ws_prims.l`: `WsLock`, `runBackground`, `threadSleep`, the `guardOn*` crash isolation and `acceptShouldContinue`. The concurrent dictionary is the pure-Lyric lock-guarded map, now in `_kernel/net/ws_dict.l` and shared by the JVM and native (dotnet keeps `ConcurrentDictionary`).
2. **JVM primitives.** `WsLock` wraps a `ReentrantLock`, never `synchronized`: a connection holds its lock across a socket write, and a virtual thread blocked in `synchronized` pins its carrier on JDK 21 (the same reasoning as `Std.HttpServerHost` and `_kernel_jvm/task.l`). `runBackground` starts a virtual thread through a record implementing `java.lang.Runnable`. Handlers are isolated with `catch Bug`. The extern aliases carry a `J` prefix because a same-named `extern type` in two files of one package leaks across `@cfg` selections on the JVM (#5443). `Ws.Kernel.Net` stays three-plus files, one package, not a reuse of `Std.HttpServerHost`: that seam is `@experimental` (D780 item 5) and S7a does not couple lyric-ws to it. Consolidating the prims files remains an S7-or-later decision.
3. **`Ws.Kernel.Jvm` stays, reduced, until S7b.** `lyric-web` on the JVM still serves HTTP through Undertow and mounts `Web.addWebSocket` endpoints with `Ws.Kernel.Jvm.endpointHandler`; deleting the kernel in S7a would break `Web.addWebSocket` on the JVM (and lyric-ui's web host). What S7a deletes from it is everything `Ws.startServer` used: `startServer`, `createRegistry`, the Undertow server start and stop, `checkRateLimit`, and their externs. What remains is `createEndpoint`, `endpointHandler`, `send`/`broadcast`/`close`/`connectionCount`/`isConnected` for an endpoint's connections, a `stopServer` that always answers `Err` (an endpoint has no listener) and `ownsHandle`. S7b moves `Web.addWebSocket` to `Ws.Kernel.Net.adoptConnection` after S4 and S6, deletes the package and the `[maven]` table of `lyric-ws/lyric.toml`.
4. **Registries route by handle.** Handles of the Undertow endpoint kernel start at 1 000 000 000, far above the sequential handles of `Ws.Kernel.Net`, so `Ws.kernelSend`, `kernelBroadcast`, `kernelClose`, `kernelConnectionCount`, `kernelIsConnected` and `kernelStopServer` pick the kernel with `WsKernelJvm.ownsHandle` on the JVM (a `@cfg(feature = "jvm")` twin; the dotnet and native twins call `Ws.Kernel.Net` directly). The public `NativeRegistry` record is unchanged. A registry from `startServer` is always a `Ws.Kernel.Net` registry; one from `createEndpoint` is a `Ws.Kernel.Jvm` registry on the JVM until S7b and a `Ws.Kernel.Net` registry elsewhere. This is a bridge with a named end (S7b), not a final shape.
5. **#9335, the dotnet threadpool.** Every WebSocket connection holds a threadpool thread for its read loop and another for its ping loop for as long as it lives. The pool starts at one thread per core and adds one about every half second above that, so a burst of connections queued behind the growth throttle: 125 of 1 000 clients completed the handshake in the S0 baseline. `startServer` and `createEndpoint` now raise the pool's minimum (`SetMinThreads(4096, 200)`, `ensureThreadCapacity` in the dotnet prims, a no-op on the JVM and native). Threads are still created on demand; the value only removes the throttle. `Std.HttpServer`'s kernel does the same with 200, which is enough for one thread per connection but not for two.
6. **Tests.** `tests/ws_dotnet_e2e_tests.l` becomes `tests/ws_e2e_tests.l` (`Ws.WsE2eTests`) and runs on dotnet, the JVM and native: the dotnet-only `Thread.Sleep` extern is replaced by `Std.Time.sleepMillis`. Three tests are added: a listed origin is admitted (ignoring case) and an unlisted one refused over the wire (the coverage `ws_jvm_origin_smoke.l` gave the Undertow server); 250 simultaneous connections all complete the handshake within 5 s (#9335's regression test; without the threadpool change it does not finish on dotnet); and an endpoint registry and a server registry coexist and each reaches only its own connections (the handle routing of item 4). The throwing-handler check is a no-op on native (no unwinding, D-N-003), as the S2 tests do for their guard checks. `tests/ws_jvm_origin_smoke.l`, `scripts/ci/lyric-ws-undertow-jvm-smoke.sh` and its `ci.yml` step are deleted; `jvm-ecosystem-suites.sh` runs every `lyric-ws` suite, and `native-web-smoke.sh` runs the loopback and codec suites on native.
7. **Compatibility.** `Ws.startServer*`, `Ws.createEndpoint`, `Ws.checkRateLimit` and every other public signature are unchanged. Behaviour differences on the JVM, all of them fixes: fragmented messages are reassembled, a ping is sent every `LYRIC_CONFIG_WS_SERVER_PINGINTERVALMS` (default 30 s), text and frame validity are enforced by `Ws.Frame` (strict UTF-8, RSV bits, control-frame rules) instead of the JDK's lenient decoding, and the connection id and handshake header handling are those of dotnet. `Ws.Kernel.Jvm.startServer` and `createRegistry` no longer exist (the package was not a public API: `Ws` is the surface). Q12 of docs/73 (clean break on the Maven coordinates) is S7b's.

## Not decided here

`startServerTls` (docs/73 question 8), slow-consumer handling and the connection cap (S8), permessage-deflate (question 7) and Autobahn (S8) are unchanged: `Ws.startServer` is plain `ws://` on every target, as on dotnet and native before. `lyric-ws/lyric.toml` still has no `[package] targets`; native runs the aspect-weaving suite no better than before (A0045, #3498).

## Consequences

- `Ws.Kernel.Jvm` shrinks from 921 to 745 lines (most of the rest is the endpoint's frame and listener plumbing that S7b deletes) and the JVM gains 150 lines of prims; the JVM server is the code dotnet and native run, so a fix in one is a fix in all.
- The B7 figures of this slice are in `docs/progress/2026-11-25-lyric-ws-jvm-tcphost.md`.
- Until S7b, a JVM application that mounts a socket on a `lyric-web` router still needs Maven and Undertow for it; one that uses `Ws.startServer` alone does not use Undertow at run time, but `lyric-ws`'s manifest still declares the coordinate.
