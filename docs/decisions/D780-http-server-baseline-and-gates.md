# D780 - The HTTP server baseline, the performance gates, and what the docs/73 spikes settled (docs/73 slice S0)

**Status:** accepted. Extends D621 (the S1 slice of the same plan); supersedes nothing. The plan (`docs/73-jvm-pure-lyric-server-plan.md`) numbers its slice decisions D614 to D618; those ids were taken by other work before S0 ran (D614 to D621 exist), so each later slice takes the next free id and cites this one.

## Context

docs/73 replaces the JVM `com.sun.net.httpserver` kernel and the Undertow bindings of `lyric-web` and `lyric-ws` with one shared pure-Lyric driver over `Std.HttpEngine` and `Std.TcpHost`. S0 records the baseline before anything is deleted, runs four spikes, and fixes the acceptance gates. Numbers, method and raw figures are in `docs/progress/2026-11-24-http-server-baseline.md`; the harness is `benchmarks/http_server/` and `scripts/ci/http-server-benchmark.sh`.

Measured on one 4-core Xeon container (JDK 21.0.12, .NET 10.0.15, clang 18), load generators on the same machine (`wrk` 4.1.0 and `h2load` 1.59.0 extracted from the Ubuntu archive packages, plus a Lyric generator), toolchain = the v0.7.15 compiler with the stdlib sources and bundle built from `origin/main` at `08f8f1a44`. The headline figures, `wrk -t4 -c64` over 20 s after a warm-up, `GET /hello`:

| | dotnet engine | JDK server kernel (as shipped) | same, `sun.net.httpserver.nodelay=true` | Undertow via lyric-web | native |
|---|---|---|---|---|---|
| B1 req/s, p50 / p99 ms | 152 858, 0.33 / 12.2 | 1 440, 44.0 / 48.1 | 71 164, 0.80 / 4.1 | 91 298, 0.57 / 7.2 | 40 794, 1.78 / 6.1 |
| B4 h2load req/s, mean ms | 58 379, 5.1 | h1 only | h1 only | 34 371, 8.8 | h1 only |

## Decision

1. **Reference for every gate: Undertow through lyric-web, measured by the same harness on the same machine class.** The thing being replaced is the baseline; the dotnet engine is reported next to it and is not the gate (it would be a different machine-class argument on every runner). The shipped JDK kernel is not a gate: it leaves Nagle on, so every keep-alive response stalls about 44 ms behind the client's delayed ACK (1.4k req/s against 71k with `sun.net.httpserver.nodelay=true`), which makes it a bad baseline and not a target to match. It is deleted in S4.
2. **Gates for S4 (the shared driver on the JVM), each against the Undertow cell measured in the same run, on the same runner:**

   | | Gate |
   |---|---|
   | B1 | at least 60% of Undertow req/s and p99 within 2x |
   | B2 | at least 60% of Undertow req/s, zero errors (with `wrk`, no read errors) |
   | B3 | at least 50% of Undertow req/s, p99 within 2x, server RSS within 1.5x |
   | B4 | at least 60% of Undertow `h2load` req/s, mean latency within 2x, zero failed requests |
   | B5 | 10 000 idle connections: RSS within 1.5x of Undertow, every idle connection still answers afterwards, zero failed trickle requests, trickle p99 within 2x |
   | B6 | a 30 minute run at half the B1 rate with connect churn: zero errors, flat thread and fd counts, RSS growth at most 10% between minute 5 and the end |
   | B7 | 1000 WebSocket clients: all connect, no message loss, delivery p99 within 2x of Undertow's |

   At the 2026-11-24 baseline that means B1 at least 54.8k req/s and p99 at most 14.3 ms, B3 at least 3 730 req/s, B4 at least 20.6k req/s with mean at most 17.5 ms, B5 RSS at most 388 MB and trickle p99 at most 6.5 ms. The thresholds are ratios, so they are re-derived from a fresh Undertow run whenever the runner class changes; the absolute figures above are the 2026-11-24 container's. B1 and B3 fall back to the optional push entry point (open question 5) before a regression is accepted, as docs/73 section 4.4 already says.
3. **Gates for S3 (the shared driver on dotnet)**: no cell worse than 90% of the pre-refactor dotnet figure in the same run, as docs/73 says. B5 is excluded until the dotnet thread-per-connection limit below is addressed; it is a tracked defect of the existing kernel, not a regression budget.
4. **Q2, package split.** Confirmed: `Std.HttpServer` (shared Lyric) plus `Std.HttpServerHost` (kernel, three twins) loads and runs on the JVM and native source loaders, and on dotnet once both packages are registered in `lyric-stdlib/lyric.full.toml`; `--internal-perpackage-build` then emits `Lyric.Stdlib.<Pkg>.dll` for each (the JVM toolchain bundles one JAR and has no per-package emit, so that clause of the plan does not apply there). The #5932 multi-file hazard no longer exists (fixed in D-progress-889), so a same-package split is also possible on the JVM, but two packages stay the choice: they match `Std.Http`/`Std.HttpHost` and `Std.Tls`/`Std.TlsHost`. Two corrections to the plan follow from the spike:
   - the seam function cannot be called `spawn` (a reserved keyword, P0051); it is `startTask`;
   - until S5 deletes the native kernel, the shared driver file lives at `lyric-stdlib/std/_kernel/http_server.l`, where the dotnet kernel is today, and moves to `lyric-stdlib/std/http_server.l` as the last step of S5. The source loaders merge same-package files from the top-level directory and the kernel directories; only `_kernel_jvm/<name>.l` and `_kernel_native/<name>.l` shadow a `_kernel/<name>.l` of the same basename, never a top-level `std/<name>.l`. A top-level shared file next to `_kernel_native/http_server.l` is therefore a duplicate declaration on native (verified: `T0001 duplicate name` on the JVM, a misleading `N0007` on native). The plan's S3 text, which assumed the native override would still win, is amended.
5. **Q3, seam visibility.** `Std.HttpServerHost` is a stdlib package marked `@experimental`, not a new public `Std.Sync`/`Std.Thread` module. An ecosystem package may import it, but the contract is not stable until S7 shows whether `lyric-ws` and `lyric-grpc` want the same primitives; consolidating `ws_prims.l`, `web_prims.l` and the seam is a separate decision then. `lyric-ws` keeps its three-file prims pattern in S7a.
6. **Q4, `nextContext` after `stopListener`.** Keep the signature and make the behaviour deterministic: after `stopListener` returns, `nextContext` panics with a documented message and never blocks. Add `tryNextContext(l): Option[HttpContext]`, which returns `None` once the listener is stopped and its queue drained, for loops that must end cleanly. `lyric-web`'s accept loop moves to the `Option` form in S6.
7. **Q5, push dispatch.** Not part of the first slices. Decided at the S4 gate: if B1 or B3 miss the thresholds above and the profile shows the pull hop, `serveHandler(listener, handler)` is added as an additive API; otherwise it is not. The baseline cannot isolate the hop (the JDK kernel and Undertow differ in far more than dispatch).
8. **Q6, `stopListener` blocking.** One contract on every target: it returns once the listener is closed, every connection registered at the call has been shut down, and their connection threads have exited, bounded by a grace period (`LYRIC_HTTP_STOP_GRACE_MS`, default 5000); a context already handed to a caller by `nextContext` stays the caller's obligation, as on every target today.
9. **Q9, connection cap.** The cap default becomes a per-target constant behind the host seam (`defaultMaxConnections()`), overridable by `LYRIC_HTTP_MAX_CONNECTIONS`: 10 000 on the JVM (virtual threads: Undertow, the JDK kernel and the planned driver hold 10 000 idle connections in 250 to 260 MB with 28 to 35 threads), 1 000 on dotnet and native, where each connection costs an OS thread (native held 10 000 with 10 042 threads in 185 MB, dotnet could not serve them, see the defects below). One portable default was rejected: it would either cap the JVM at what a pthread build can afford or let native and dotnet exhaust threads.
10. **Q10, test shim for the puller thread.** No extern shim is needed. `Std.Task.makeScope` and `scopeSpawn` start real concurrent tasks on dotnet (threadpool), the JVM (virtual threads) and native (threads); the server, load generator and spike programs of S0 use only that and run on all three. The neutral server tests use it directly.
11. **Questions S0 leaves as the plan has them**: 7 (permessage-deflate), 8 (`startServerTls`), 11 (shared h2 scheduler for gRPC), 12 (clean break on `Ws.Kernel.Jvm`), 13 (header casing). None depends on S0's measurements.
12. **Spike (c) is closed as not reproducible.** The cross-error-type JVM miscompile that `lyric-web/src/web.l` (~2455) documents does not occur on the v0.7.15 compiler, neither in the exact shape of the shared `serveTls` against the real `Std.HttpServer.TlsListenError` nor in a two-package user-union variant that matches by call, by case and by nested pattern. S6 still carries a JVM regression test for the mTLS-misconfiguration path of `Web.serveTls` and removes the stale comment.
13. **Spike (b) is closed.** JDK 21.0.12: virtual threads blocked in an `SSLSocket` read through `Std.TcpHost` are parked, not pinned: 32 concurrent TLS connections are served on a one-carrier scheduler (`parallelism=1`, `maxPoolSize=1`) and `-Djdk.tracePinnedThreads=full` prints nothing. The h2 driver's blocking semaphores stay with `ReentrantLock`-based primitives (never `synchronized`), as the plan already requires.
14. **Tooling.** `wrk` and `h2load` are not installed on the CI image or in the dev container, but both come from the Ubuntu archive (`apt-get download wrk nghttp2-client` plus their library packages, extracted with `dpkg-deb -x`, no install) where `archive.ubuntu.com` is reachable, and `nghttp2-client` is a one-line `apt-get install` on the hosted ubuntu runners. The driver script uses them when on `PATH` and otherwise falls back to the Lyric generator and `curl --http2 --parallel`; the Lyric generator reached about half of `wrk`'s rate on dotnet, so it is a fallback, not the gate's instrument. Docker is installed in the dev container but its daemon is not running and no workflow job uses a container image today; Autobahn (S8 iv) therefore needs a job that starts Docker on a hosted runner, which is unverified here.

## Defects found by the baseline (each becomes a tracked issue; none is fixed by S0)

- The JDK `Std.HttpServer` kernel stalls every keep-alive request about 44 ms (Nagle against delayed ACK). Deleted in S4; a one-line `System.setProperty("sun.net.httpserver.nodelay", "true")` before the first server is created fixes it in the meantime.
- The dotnet `Std.HttpServer` kernel serves only as many connections as the threadpool has threads: with 10 000 idle keep-alive connections held, new connections got no service (0 of 8 trickle requests in 20 s, 248 threads) and the idle ones answered only as earlier connections closed. S3 must decide how the shared driver avoids this on dotnet.
- The native `Std.HttpServer` kernel completes no request when 64 connections arrive per-request (`Connection: close`): `wrk` reads 1.4M resets and 0 responses, and its RSS jumps to about 412 MB and stays (about 12 KB per accepted connection) after the first tens of thousands of connections. It works with 8 or fewer concurrent connections. S5 inherits this.
- The dotnet `lyric-ws` kernel completes the handshake of only 125 of 1000 clients with the default threadpool (Std.HttpServer's kernel raises the minimum thread count; the ws kernel does not). With the minimum raised, 999 of 1000 connect, p50 7 ms, p99 49 ms.
- Released v0.7.15's compiled dotnet stdlib bundle predates D621 and lacks `TCP_NODELAY`: h2 over TLS there showed a 43 ms latency floor (1.1k req/s against 12.7k with the bundle built from `main`). Not a defect of `main`, but a reason the baseline is only valid with the toolchain described above.

## Consequences

- S1, S2, S3, S4, S5, S6, S7a/b, S8, S9 keep their scope; the amendments are the location rule and seam name (S2, S3), the dotnet-B5 exemption (S3), the per-target connection cap (S3, S4), `tryNextContext` and the stop contract (S3), and the regression test for the cross-error match (S6).
- The benchmark harness stays in the tree and is run by hand or nightly; it is not a CI job (the workflow has about 500 bytes of headroom).
- `docs/61` section 6.5 criterion (c), "throughput within a documented factor of the `HttpListener` baseline", is satisfied by the gate table above in place of the `HttpListener` baseline, which no longer exists.
