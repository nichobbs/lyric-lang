# D-progress-1056 — Every unhinted bracket literal with a non-literal element is built at its checked slice type

**Status:** shipped (completes D-progress-1055)

**Problem.** D-progress-1055 fixed an unannotated `val`/`var`/`let` initializer. The same `List<object>` was still built wherever the type checker types a bracket literal with nothing expected and the backend cannot peek an element's type (a call, a member access, an index): the result of a lambda (`{ -> ["a", n.toString()] }`, with or without parameters, block tail or `return`), a tuple element, an argument of a generic constructor (`Some(value = [...])`, `Box(v = [...])`), the receiver of a slice method (`[...].toArray()` printed an empty string; `.concat`/`.slice` failed with `unsupported method ... on the receiver type`), and an element of another literal used as a `for` iterable. Measured on the build of D-progress-1055: lambda result, tuple element, `for` iterable, `Some`, `Box`, `toArray` receiver printed an empty string or crashed with `AccessViolationException`.

**Decision.** `recordListLiteralType` (called from the `EList` arm of `inferExprCore`) records the checked type in `SymbolTable.listLiteralTypeSites` for every closed slice type, not only slices of generic instantiations, when an element is not itself a literal (`allLiteralElements`) and the literal is not in a contract clause. `Lyric.Mono` then binds the literal to a local of that type, and the `MArray` arm builds the array, exactly as for an annotated binding. No new IL and no new syntactic inference; `recordLocalSliceLiteralTypes` (D-progress-1055) stays, and covers a binding of a literal of literals.

**Hinted positions win, measured.** The first form of this change recorded every unhinted literal and withdrew nothing. Measured result: `sum([1, 2, n])` for a `slice[Long]` parameter printed `8589934600` (it built an `int[]`, read as `long[]`): the literal had been checked bottom-up as `slice[Int]` as well as against the parameter, and the bottom-up record bound it at a type its position did not ask for. So the arms of `inferExprExpected` that consume an expected collection type (a numeric `slice[T]`, an `array[N, T]`, any other `slice[T]` annotation or tuple element, and a `List`) now withdraw the site with `noteListLiteralInListContext` (a conflicting record is never bound), unless the element type holds a generic instantiation, which a position does not build and which was always recorded. After that change the `slice[Long]`, `slice[Double]`, annotated tuple, annotated lambda, annotated `Option`, annotated binding and range-subtype cases build as before (`position-matrix`, B2 report). A literal an enclosing literal's `recordSliceShapedElement` shapes takes that shape over a withdrawn record (`recordListLiteralSite`).

**Scope limits.** A literal of literals (`["a", "b"]`, `[1, -2]`) is not recorded: the backend reads its type off the elements, and recording it would rewrite most literals in the compiler for nothing. A literal in a contract clause is not recorded: the verifier reads the clause as written. An open literal (`[]`, element type not closed) is not recorded.

**A conversion where the codegen holds a slice as `object`.** A closure call is lowered on the uniform `Func<object, ..., object>` ABI: its result is an `object`, and `materializeBoxedElemMsil` left a slice result (`MArray`) uncast, so `pathCombine(g())` passed an `object` where `String[]` was declared (`ilverify` StackUnexpected, found `object`, expected `string[]`, in the new lambda tests) and, for a `List`-backed slice, a `List` at runtime. `lowerFuncValueInvokeMsil` now converts a slice result whose element type has an array token with `emitObjectToSliceArrayMsil`, the existing both-shapes conversion (`isinst e[]`, else copy the `IList` into a fresh `e[]`; a slice is never written through, so the copy is unobservable). The same conversion already narrowed a bound tuple element and a lambda parameter. A List-backed slice returned by a closure now reaches a `String[]` parameter as an array (`slice_fastpath_listbacked_dotnet_self_test.l`).

**Not done: a conversion at every `object` to `T[]` call argument.** `coerceCallArgMsil` still emits nothing there. A plain `castclass T[]` would reject an `object[]` read as a `String[]` that works by luck (not tested here); the both-shapes conversion would be correct but no remaining position needs it, and an untested codegen path was not added. It is the way to close a position nobody has enumerated.

**Backends.** The JVM binds only shape-required sites, so its output is unchanged; native binds all sites and lowers from checked types, so it receives the new sites and a typed local for the same literal.
