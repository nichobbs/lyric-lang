# D791 - lyric-web serves through the shared `Std.HttpServer` driver on every target; its Undertow kernel is deleted (docs/73 slice S6)

**Status:** accepted. Extends D789 (the JVM adopts the shared driver, S4), D788 (the shared driver, S3), D787 (lyric-ws on the JVM over `Std.TcpHost`, S7a) and D780 (baseline and gates); resolves spike (c) of D780 in lyric-web. The plan numbered this decision D617; that id was taken, so it takes the next free one (D790 is S5, PR #9355). S5 (D790) has merged: native has `tryNextContext` and the driver lives at `lyric-stdlib/std/http_server.l`.

## Context

After S4 the JVM `Std.HttpServer` was the shared driver, but `lyric-web` on the JVM still bound `io.undertow` in a 541-line kernel (`_kernel/jvm/web_kernel.l`: `Undertow.builder()`, a Lyric record implementing `HttpHandler`, request and response translation, `addHttpsListener` with `ENABLE_HTTP2`, XNIO client-auth options, a virtual-thread worker loop) and declared `io.undertow:undertow-core` in `[maven]`. `Web.serve` and `Web.serveTls` each had a second, JVM-only definition, `serveStreaming` and `startStreaming` did not exist on the JVM, and `Web.addWebSocket` mounted its endpoint on an Undertow `PathHandler` through `Ws.Kernel.Jvm`.

## Decision

1. **One accept loop, no `@cfg` in the server section.** The 39 `@cfg(any(feature = "dotnet", feature = "native"))` annotations of the serve section of `web.l` are deleted (not widened: with `jvm` included they would name every target). `serve`, `serveStreaming`, `serveTls`, `start`, `startStreaming`, the streaming types and the request jobs now compile on dotnet, the JVM and native. The JVM-only `serve` and `serveTls` (about 40 lines) and `_kernel/jvm/web_kernel.l` are deleted. The per-target code left in lyric-web is the static-root `pathGetFullPath` (a seam, unchanged) and `Web.Kernel.Runtime`.
2. **`Web.Kernel.Runtime` is one shared file plus two prims files.** `_kernel/net/web_kernel.l` (rate limiter, `startWorkerLoop`, `spawnRequestJob`, `upgradeWebSocket`) is compiled on all three targets over `Ws.Kernel.Net`'s `runBackground` and locks, which already cover the JVM since D787; `_kernel/net/web_prims.l` (the `try`/`catch Bug` isolation family) is compiled on dotnet and the JVM, `_kernel/native/web_prims.l` on native. The manifest entry for the JVM file is gone, and with it the #5443 alias-collision exposure (no two files declare an extern alias any more). The worker loop on the JVM is a virtual thread started by `runBackground`, replacing `WorkerLoopRunnable` over a `newVirtualThreadPerTaskExecutor`.
3. **`[maven]` is removed from `lyric-web/lyric.toml`.** The feature comments say what the features now mean. lyric-web itself neither compiles against nor loads Undertow. **A JVM build of lyric-web still restores Undertow's jars**, because `lyric-ws`, a dependency, keeps its `[maven]` table and the unreachable `Ws.Kernel.Jvm` (decision 6); `lyric restore` is transitive (D311), so the CI scripts keep their `make maven-resolver` and `restore` steps until S7b. The plan's acceptance line "no CI step restores Undertow for lyric-web" is therefore not met yet and is recorded as such.
4. **`tryNextContext`, and a loop that can end.** `PlainAcceptLoop` and `TlsAcceptLoop` pull with `tryNextContext`. They carry an `AcceptState` (`ended`) that `step` sets when the listener reports it was stopped and that `fail` sets after it stops the listener and sets exit code 1; `serve`, `serveStreaming` and `serveTls` loop `while not state.ended`. Before, a failed listener was stopped and the `while true` loop then called `nextContext` again, which panics after a stop, so `fail` logged the same line in a tight loop. Now `serve` returns (exit code 1) and `serveTls` returns `Ok(())` after a listener failure; the documented contract "blocks for the life of the process" is unchanged in normal operation. `AcceptLoop` and `RequestJob` (public, `@stable(since = "0.3")`) keep their method sets; the state lives in the records, so no public signature changed. Nothing in this repository or `lyric-ecosystem` implements them.
5. **`serveTls` is one function and the stale comment is gone.** The shared `serveTls` matches `Std.HttpServer.startListenerTls`'s `Result[HttpListener, TlsListenError]` inside a function returning `Result[Unit, ServeTlsError]` and takes the reason through `TlsListenError.message` (a call, resolved in `Std.HttpServer`; D789 gave the JVM that function). The comment claiming the JVM backend miscompiles that shape (the #5903 family) is replaced by a note that spike (c) of D780 could not reproduce it and that `serve_tls_tests.l` pins both start-failure paths on every target. The message of the JVM misconfiguration error changes from the lyric-web-specific text to `lyric-web serveTls could not start an HTTPS listener on <host>:<port>: <InvalidConfig message>`, the same text as dotnet.
6. **`Web.addWebSocket` runs over `takeConnection` on the JVM, which makes S7b small.** An Undertow `PathHandler` cannot be mounted on a port the shared driver owns, so S6 could not leave the JVM's WebSocket path alone. The shared `serveWebSocketUpgrade` and `HttpKernel.upgradeWebSocket` (`takeConnection` then `Ws.Kernel.Net.adoptConnection`) now run on the JVM, and `lyric-ws`'s `kernelCreateEndpoint` allocates a `Ws.Kernel.Net` registry on every target instead of a `Ws.Kernel.Jvm` one (`ws.l`: one function replaces the two `@cfg` variants, the only lyric-ws source change). `web_socket_tests.l` runs on dotnet and the JVM (it used a dotnet `Task.Run` and `Thread.Sleep`, now `startTask` and `sleepMillis`): 4 tests on each. **S7b is now only deletion:** `lyric-ws/src/_kernel/jvm/ws_kernel.l`, its `Ws.Kernel.Jvm` package entry and `[maven]` table in `lyric-ws/lyric.toml`, `import Ws.Kernel.Jvm as WsKernelJvm` and the `ownsHandle` routing wrappers of `ws.l` (D787 item 4), the Undertow mentions in `lyric-ws/README.md`, and the Maven restores of `jvm-ecosystem-suites.sh` (`web` and `ws` entries), `lyric-web-smoke.sh`, `ui-jvm-suites.sh` and `ci.yml`.
7. **Behaviour changes on the JVM, all intended** (the first four are D789's, now reaching lyric-web): HTTP/2 over ALPN on `serveTls` listeners; mTLS through `Std.HttpServer`; request header names keep the client's capitalisation (`Web.header` folds case); the body cap is the engine's `EngineLimits.maxBodyBytes`; `serveStreaming`/`startStreaming` and chunked streaming work; `Web.addWorker` fires with per-tick isolation through the shared `runBackground`; a handler panic on the JVM is isolated by `runJobGuarded` and answered with a 500 as on dotnet; the connection cap is `LYRIC_HTTP_MAX_CONNECTIONS` (default 10 000 on the JVM) where Undertow had its own worker pool; `serve` returns when the listener fails (decision 4). Code that reached into `Web.Kernel.Runtime.serve`/`serveTls` (package-level, never documented API) no longer compiles.
8. **Tests.** `jvm_server_smoke.l` becomes `web_smoke.l` (package `Web.WebSmoke`, no extern: its background threads are `Std.HttpServerHost.startTask`), run on dotnet and the JVM by the new `scripts/ci/lyric-web-smoke.sh <dotnet|jvm>`, which replaces `lyric-web-undertow-jvm-smoke.sh` and also runs `serve_failure_tests.l` (crash isolation) and `streaming_tests.l` (chunked responses, the middleware gate; its dotnet `Thread.Sleep` extern became `Time.sleepMillis`) on the selected target, so streaming is exercised on the JVM. `concurrent_dispatch_tests.l` (#7997) was dotnet-only and now runs everywhere. The per-target start helpers of `serve_crash_isolation_tests.l`, `worker_dispatch_tests.l`, `serve_tls_tests.l` and `concurrent_dispatch_tests.l` (a dotnet `Task.Run` extern and a JVM `Runnable` record plus executor each) are one `startTask` call. `serve_tls_tests.l` gains the JVM regression test D780 asked for in two forms: the mTLS misconfiguration (asserting the message prefix and that it names `requireClientCert` and `clientCa`) and a port that is already bound, both going through `startListenerTls`'s `Err` into `ServeTlsError`; 9 tests on dotnet and on the JVM.
9. **The benchmark script learns lyric-web on every target.** `scripts/ci/http-server-benchmark.sh` replaces the `undertow` target with `web-dotnet`, `web-jvm` and `web-native`, all building `benchmarks/http_server/server_web.l` (native through a generated throwaway application manifest, because a file inside the library manifest does not resolve `Web` on native, T0215). The Undertow figures below were measured with this script on `origin/main` before the change.

## Verification

`lyric test --manifest lyric-web/lyric.toml`: dotnet 103 tests in 10 suites, JVM (`--target jvm --no-default-features --features jvm`) 102 in 10 suites (the dotnet-only `HttpCircuitBreaker` aspect case, #3669, is the difference), `Web.WebSocketTests` 4 on each. `scripts/ci/lyric-web-smoke.sh dotnet` and `jvm`: the four endpoints, the 10 MiB cap (exactly at the limit echoed, 413 over it for `Content-Length`, chunked and GET), `HTTPS-H2`, `MTLS-MISCONFIG`, `MTLS-ACCEPT` and `MTLS-REJECT` self-checks, `curl --http2` `2:200`, crash isolation (`/crash` 500 and the server survives), chunked streaming. Native, on the merged tree (S5 is on main): `scripts/ci/native-web-smoke.sh` passes (HTTP routes, the static-root symlink checks, a raw RFC 6455 echo through `takeConnection`, and lyric-ws's 4 native suites). `lyric test --manifest lyric-web/lyric.toml --target native --no-default-features --features native`: `Web.CorsGuardTests` 17, `Web.RateLimitTests` 5, `Web.DispatchTests` 44, `Web.ServeTlsTests` 9, `Web.WebSocketTests` 4, `Web.ConcurrentDispatchTests` 1 and the first `Web.WorkerDispatchTests` case pass. Four cases fail or do not build on native for reasons that are not S6's: `Web.SecurityAspectWeavingTests` does not compile (A0045, cross-package aspect templates are not resolved on native, #3498), and the three panic-isolation cases (`Web.ServeCrashIsolationTests`, the panicking-tick case of `Web.WorkerDispatchTests`) and `Web.WebTlsConfigTests` test 2 (config env override) fail because native has no unwinding (D-N-003) (and, for the env-override case, for a reason I did not investigate); they were never run on native before and are not skipped or disabled, the manifest suite is simply not yet a native suite. `serve_failure`/`streaming`/`web_smoke` were run on dotnet and the JVM only; `audit-axioms.sh`, `audit-kernel-stubs.sh` and `check-workflow-size.sh` pass (ci.yml 490 692 bytes, 785 fewer).
