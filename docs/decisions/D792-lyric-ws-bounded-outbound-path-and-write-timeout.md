# D792 - lyric-ws: a bounded outbound queue and a write timeout, so one slow consumer stalls only itself (docs/73 slice S8, item i)

**Status:** accepted. Extends D787 (the pure-Lyric server on every target) and D780 (gate B7). Closes the "backpressure and slow consumers" row of docs/73 section 3.

## Context

`Ws.Kernel.Net` wrote every frame on the calling thread, under the connection's lock, with no I/O timeout (`hostSetIoTimeout(conn, 0)`). A peer that stopped reading filled its socket buffers and the next `hostWrite` to it blocked forever. `broadcast` was a serial loop over the connections, so that one write stalled every other client's delivery, and so did `send` from a handler. Measured on the unmodified server (dotnet and the JVM, 50 clients that read plus 2 that complete the upgrade and never read, 60 000-byte text frames at 10 Hz, 30 s): the readers stopped receiving after about 67 of 299 broadcasts (3 350 messages in total instead of 14 950) and one `broadcastText` call took 23.4 s.

## Decision

1. **One queue per connection, one writer at a time.** Every outbound frame (data, the keepalive ping, the Close reply and an application `close`) is appended to the connection's queue (`ConnState.queue`, counted in `queuedBytes`). `enqueueFrame` returns as soon as the frame is queued; a drain task, started when the queue goes from empty to non-empty and ended when it empties, is the only code that calls `hostWrite` after the upgrade. Frames therefore never interleave, and a stalled peer blocks its own drain task and nothing else. `ConnState.lock` guards the fields and is never held across a socket operation (it used to be held across the write).
2. **A bound on the backlog.** `WsServerOptions.maxOutboundBytes` (default 1 MiB, at least 1024). A data frame that would take `queuedBytes` past it while something is already queued drops the connection as a slow consumer: `send` returns `Err("slow consumer: ...")`, `onError` is told, the queue is discarded, the socket is shut down (`hostShutdown`, which interrupts the blocked write on every target) and `onClose` reports 1008. A frame is always accepted into an empty queue, so a message larger than the bound is not refused for its size alone. Control frames are exempt, so a Close or a Ping is never refused.
3. **A write timeout.** `WsServerOptions.writeTimeoutMs` (default 10 000, `0` = off). The drain task stamps `writeStartNs` around each `hostWrite`; the connection's maintenance task (the old ping loop, now always running) ends the connection (`onError` "slow consumer: a write made no progress for N ms", `onClose` 1008) when a write has been in flight longer than that. This covers a peer that stops reading while the queue still has room, and a single frame larger than the socket buffers. It is implemented in the kernel over `hostShutdown` and `Std.Time.monotonicNanos` rather than `hostSetIoTimeout`, because that call sets the read and the write timeout together on every target (one value for both), and a read timeout would end a quiet but healthy connection. The check runs every quarter of the shortest enforced period (10 ms to 1 s).
4. **`broadcast` encodes once and queues for each connection**, never writing to a socket itself. It still returns `Err` with the first failure (a connection closed meanwhile, or a slow consumer it dropped) after attempting every connection, as before.
5. **`send` and `broadcast` mean "queued".** `Ok` no longer implies the bytes reached the socket. A send to a connection that is closing (a Close frame already queued) or aborted is `Err`; previously data could be written after a Close frame.
6. **Ordering and teardown.** The Close reply to a peer's Close is queued and `finishConnection` waits for the drain task to end before it releases the socket (`waitDrained`: up to 5 s, then the socket is shut down so the write fails; the wait continues until the task has ended, because a task must never write to a descriptor its owner has closed). `ConnState.released` is set, under the lock, before `hostClose`, and `abortConnection` checks it under the same lock before `hostShutdown`, so a late watchdog never shuts down a reused descriptor on native. A close that the peer never answers is shut down after 5 s (previously the connection waited forever).
7. **Source compatibility.** `WsServerOptions` gains defaulted fields; `send`, `broadcast`, `WsRegistry` and the kernel's existing entry points keep their signatures (`Ws.Kernel.Net.startServer` and `createEndpoint` call the new `startServerWith` and `createEndpointWith` with `defaultLimits()`). The one behavioural change is item 5. Applications that relied on `send` blocking as backpressure now get `Err("slow consumer")` and a dropped connection instead of a stall.

## Verification

- `tests/ws_hardening_tests.l` (`Ws.WsHardeningTests`), which fails with the bound or the watchdog removed (verified by mutation: three tests fail): a stopped client beside a healthy one over 25 MB of 128 KiB broadcasts (every `broadcast` call under 1.5 s, worst 6 to 34 ms measured, the healthy client receives all 200 frames in order, the stopped one is dropped with 1008 and "slow consumer" in `onError`); a write timeout with a 64 MiB queue bound (16 MiB queued without waiting, connection ended with "no progress"); a 1 KiB bound (`send` reports the slow consumer, later sends fail). dotnet 12, JVM 12, native 13 of 13.
- B7 (`benchmarks/http_server/ws_server.l`, `ws_clients.l`, which gained `WS_STALLED` and a `worst_call_ms` report), same container, loopback, 4 cores:

| | before | after |
|---|---|---|
| dotnet, 1000 clients, 1 KiB at 10 Hz: connected / p50 / p99 / max | 1000 / 8 / 52 / 100 ms | 1000 / 7 / 16 / 73 ms |
| JVM, same | 993 to 1000 (up to 7 failed connects) / 12 / 33 to 36 / 136 ms | 997 to 1000 / 7 / 15 to 20 / 129 to 182 ms |
| dotnet, 50 clients + 2 stalled, 60 000 B at 10 Hz: messages / per client / p99 / worst `broadcast` call | 3 348 / 66 to 67 of 299 / 180 ms / 23 360 ms | 14 950 / 299 / 24 ms / 5 ms |
| JVM, same | 3 350 / 67 / 110 ms / 23 452 ms | 14 900 / 298 / 28 ms / 18 ms |

The JVM client fleet loses a few connects under 1000 simultaneous dials with either server (listen backlog 128); that is not a regression. Single runs on a shared container: differences under about 10% are noise. Native was not benchmarked (the client fleet is JVM-only); its behaviour is covered by the 13 native tests above.
