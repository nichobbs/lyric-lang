# D-progress-1055 — An unannotated binding's list literal is built at its checked slice type

**Status:** shipped

**Problem.** On MSIL a `slice[T]` is a real CLR `T[]` wherever the position names the type (an annotated binding, an argument, a return, a field) and a `List`-backed value otherwise; a function of this compilation unit takes it as an erased `object` and reads it through `IList`, so it tolerates either, while an `@externTarget` binding and a function of another assembly declare `T[]` and read the array fields of whatever they are handed. The no-hint `EList` arm guessed the representation from the elements' syntax, and for an element it could not type (a call, a member access, an index) it built a `List<object>`. An unannotated `val parts = ["a", n.toString()]` then reached a `String[]` parameter as a `List`, with no conversion and no cast: memory-unsafe (`AccessViolationException`, garbage lengths, silent empty results).

**Decision.** The literal's type is the checker's, not a guess from syntax. For an unannotated binding no collection type is expected of the initializer, so the checker's type of it is exactly the type the binding has. `recordLocalSliceLiteralTypes` records that type for each bracket literal the initializer evaluates to (under parentheses, through `if` branches and `match` arms) in `SymbolTable.listLiteralTypeSites`, and `Lyric.Mono` binds each to a local of that type, as it already did for slices of generic instantiations (#7818, `recordListLiteralType`). The `MArray` arm then builds the array. The three binding forms (`val`, `var`, `let`) take the same path. Only a slice type that is closed and mentions no generic instantiation is recorded here; the latter keep `recordListLiteralType`.

Recording at the binding, not at every unhinted literal, is deliberate: a literal checked where a collection type is expected (a numeric `slice[Long]` argument that an integer literal widens into, a `List` parameter, an `array[N, T]`) may be checked both bottom-up and against the expected type, and a site recorded from the bottom-up check would then bind it at a type its position did not ask for (D-progress-1056 measured it: `sum([1, 2, n])` for a `slice[Long]` parameter built an `int[]`, so those arms withdraw the site). An unannotated binding is checked once, with nothing expected.

**Backends.** MSIL and native bind `listLiteralTypeSites` (`MiddleEndOptions.bindListLiteralTypes`); native lowers from checked types (`tir/build/build_expr.l`) and was not at fault. The JVM binds only shape-required sites; its literal is always an `ArrayList`, converted by `coerceArgTo` at an array-typed boundary, so it never passes the list as an array.

**Not covered here.** The other unhinted positions (a lambda result, a tuple element, an element of another literal, a `for` iterable, a receiver, a generic constructor argument) are closed by D-progress-1056, which also measured the numeric-widening hazard that paragraph left open.
