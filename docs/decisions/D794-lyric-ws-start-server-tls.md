# D794 - lyric-ws: `startServerTls`, a wss listener on every target (docs/73 slice S8, item iii)

**Status:** accepted. Extends D787, D790 (the TLS lock in `lyric-rt`) and docs/61 (the `Std.TcpHost` TLS server path). Resolves docs/73 question 8.

## Decision

1. **Surface.** `Ws.startServerTls(host, port, path, tls: Std.Tls.TlsServerConfig, options: WsServerOptions, handler): Result[NativeRegistry, WsError]`, additive. A WebSocket socket on the HTTP server's own TLS port stays available through `Web.serveTls` and `Web.addWebSocket`; `startServerTls` is for a listener of its own, as `startServer` is for ws.
2. **Over the existing transport.** The kernel calls `hostPrepareServerTls(cfg)` once, before binding, so a configuration that cannot work (for example `requireClientCert` with no `clientCa`) is `SERVER_START_FAILED` and the port is never taken. Each accepted connection is upgraded with `hostUpgradeServerTlsPrepared(plain, tls, handshakeTimeoutMs)` on its own connection task, never on the accept loop, so a client that stalls its ClientHello holds only its own slot (D793), and the upgraded `Conn` then follows the same path as a plain one (handshake, read loop, outbound queue). mTLS is `TlsServerConfig`'s own (`clientCa`, `requireClientCert`); nothing is added.
3. **Release.** `stopServer` stops the listener and releases the prepared TLS state (`hostReleaseServerTls`, which frees the OpenSSL context on native) once no handshake is using it: a count of upgrades in flight under the registry lock, the last upgrade to finish after the stop releases it.
4. **Native concurrency.** A WebSocket connection reads on one thread and writes on another (the drain task); native OpenSSL is safe for that only because of the per-connection lock D790 added to `lyric_tls.c`.
5. **What is tested where.** Every target: TLS terminates and the WebSocket server answers through it (a plain GET of the upgrade path is `400` over TLS), an untrusted CA fails the handshake, mutual TLS refuses a client without a certificate and admits one signed by the CA, a bad configuration is refused before the bind, a peer that never finishes the handshake is cut off by the handshake timeout. WebSocket frames over TLS (upgrade, echo, close) are exchanged on native only, with `hostConnectTls`: `Std.TcpHost` has no client TLS connect on dotnet or the JVM, and the JDK's HTTP client refuses an `Upgrade` header, so no test client can speak WebSocket over TLS there. The server code after the TLS upgrade is the same `Conn`-level path as `ws`, which is exercised on all three targets; adding `hostConnectTls` to the dotnet and JVM `Std.TcpHost` kernels would close the gap (issue text in the progress note).
