# D804 - `Grpc.Server`: one pure-Lyric gRPC server for dotnet and the JVM, with TLS, gzip request decode and `grpc-timeout` enforcement (docs/72 slice 8)

**Status:** accepted. Implements slice 8 of `docs/72-h2-client-role-plan.md` (§4.4). Builds on D287 (the dotnet h2c server, whose limits it lifts in part), D800 (the `Std.HttpServerHost` seam use), D789 to D791 (the shared HTTP server driver, whose TLS shape it follows), D798 (gzip) and D802 (`Grpc.Wire`).

## Decision

1. **`Grpc.Server`** (`lyric-grpc/src/server.l`, was `src/_kernel/net/grpc_server.l`, `Grpc.Kernel.Net.Server`) is the one server on dotnet and the JVM. It is `Std.TcpHost` plus `Std.HttpEngine.H2Conn` plus `Std.HttpServerHost` (`startTask`, `Mutex`, `runGuarded`, `ensureThreadCapacity`): the three dotnet externs (`Task.Run`, `Monitor.Enter/Exit`) are gone, and so is the grpc-java `Server` (`NettyServerBuilder`, `ServerCalls`, the `Context` metadata capture) in `Grpc.Kernel.Jvm`. `Grpc.start`, `startHandle`, `startHandleAt`, `serverPort` and `stop` lose their per-target `@cfg` bodies and call it. `Grpc.Kernel.Net` and `Grpc.Kernel.Jvm` keep the legacy client and the rate limiter until slice 10. Connection, drain and `maxConnectionIdleMs` behaviour is D287's (the 4 MiB limit, `trackedConnections`, a second stop is a no-op, a stop with `drainTimeoutMs = 0` closes connections under calls in flight). New: `stop` first sends GOAWAY (NO_ERROR) on every connection, so clients start no new call while the calls in flight drain; closing without it made a grpc-java client report a bare `channel closed` of a code other than `Unavailable` about two times in three (found by `server_tests.l` under `legacy-client` on the JVM).
2. **TLS.** `Grpc.startHandleTlsAt(registry, host, port, TlsServerConfig)` and `Grpc.startTls(registry, tls)` (blocking). The configuration goes through `hostPrepareServerTls` once, so a mutual-TLS misconfiguration (`requireClientCert` without `clientCa`) or an unusable identity panics at start, like a bind failure. Each accepted socket is upgraded on its own connection task with `hostUpgradeServerTlsPrepared` (10 s handshake limit), so a stalled handshake never holds the accept loop; ALPN other than `h2` (or none) is closed, since gRPC needs HTTP/2. Two monomorphic accept loops (plain, TLS) as in `Std.HttpServer`.
3. **Compression decode.** The request body is read through `Wire.MessageReader` (bounded at 4 MiB), exactly one message is required, and a compressed message is expanded with `Wire.decompressMessage` under the same 4 MiB output bound, so a decompression bomb is `ResourceExhausted` before it is built. `identity`, `gzip` and `x-gzip` are accepted; any other `grpc-encoding` is `Unimplemented` with `grpc-accept-encoding: identity,gzip`. A compressed flag with no encoding, or a body that is not gzip, is `Internal`. Responses are never compressed (kept, was D287 item 6 in part).
4. **`grpc-timeout` enforcement.** `Wire.parseTimeout` (one to eight digits and `H M S m u n`, rounded up to a millisecond; anything else `None`). A malformed value is `Internal` and no handler runs. For a call with a deadline the server starts one watcher task when the handler is dispatched: at the deadline it ends the call with `DeadlineExceeded` if the handler has not answered, and marks it cancelled so a streaming handler's `emit` returns `false`. A unary handler cannot be interrupted and runs to completion in the background; its later result is dropped. The handler receives the time left at dispatch as a `grpc-timeout` metadata entry, read with `Grpc.requestTimeoutMs(meta): Option[Long]` (`None` without a deadline). The deadline runs from the request headers.
5. **One answer per call.** Every response goes through `ensureHeaders` and `finishCall`, which take the connection mutex and test a per-call `responded` flag, so the handler task, the deadline task and a panic handler can race and exactly one ends the call. A `Bug` from the handler is caught at the task boundary with `runGuarded` and ends the call `Internal` with no detail (the text may carry server internals).
6. **Tests.** `server_h2_tests.l` (22 tests, both targets: compression, bounds, deadlines on unary and streaming calls with the client's own deadline removed so the server's enforcement is what ends the call, panic isolation including concurrent panicking and healthy calls, drain and GOAWAY, parallelism, TLS with a pinned CA, untrusted CA, plaintext to a TLS port, mTLS misconfiguration), `server_interop_jvm_tests.l` (grpc-java as the client) and `server_interop_dotnet_tests.l` (`Grpc.Net.Client`), six tests each against the independent client; `server_connection_tests.l` (was `server_dotnet_tests.l`) and `server_tests.l` now run on both targets against the one server.

## D287 limits

Lifted: request compression (item 6 in part), `grpc-timeout` enforcement (item 4), TLS (item 7). Kept: no server reflection, no response compression, unary and server-streaming only (slice 9), no gRPC-web, `Grpc.Aspects` dotnet only, a sender waits at most 30 s for flow-control credit.

## Deviations from docs/72

- The package is `Grpc.Server`, not `Grpc.Server.H2`.
- The plan named a lock from `Std.Task`; the `Std.HttpServerHost` seam is used as in slice 5 (OQ-7).
- `ensureThreadCapacity(defaultMaxConnections())` is called at server start: on dotnet the deadline watcher is a pool task and starved behind blocking handlers (a 250 ms deadline answered at 1008 ms without it).

## Not done

- TLS interop with grpc-java and `Grpc.Net.Client` (the SDK kernels expose no trust option; TLS is tested with the pure-Lyric client on both targets) and mutual TLS with a real client certificate (only the misconfiguration check is tested).
- Native (slice 7). Removing the SDK kernels and `[nuget]`/`[maven]` entries (slice 10).
