# D788 - The shared HTTP server driver, adopted by dotnet (docs/73 slice S3)

**Status:** accepted. Extends D780 (S0, the gates and the stop contract), D786 (S2, the `Std.HttpServerHost` seam) and D621 (S1). Supersedes the per-kernel statement of D128 section 6.1/6.2 ("each target writes its own accept loop"): the accept loop, the connection driver, the h2 send scheduler, the limits and the stop logic are now one Lyric file. The plan numbered this decision D615; that id was taken, so it takes the next free one.

## Context

docs/73 replaces the JVM `com.sun.net.httpserver` kernel and the Undertow bindings with one pure-Lyric driver over `Std.HttpEngine` and `Std.TcpHost`. S3 writes that driver by migrating the dotnet kernel, the most complete one (h1, h2 with the send scheduler, limits, timeouts, `takeConnection`, chunked responses, 33 tests), into a file that depends on no BCL type. The JVM and native loaders keep shadowing it with their own kernels until S4 and S5; only the dotnet loader reads it today.

## Decision

1. **The file.** `lyric-stdlib/std/_kernel/http_server.l` (package `Std.HttpServer`, D780: it moves to `std/http_server.l` as the last step of S5). It has no `extern`, no `@externTarget` and no `@axiom` (the dotnet axiom row of docs/17 is gone, 43 to 42 files); everything it needs from the platform comes from `Std.TcpHost`, `Std.HttpEngine` and `Std.HttpServerHost`. The public surface is unchanged except for two additions and one widened behaviour below.
2. **Seam additions (amending D786).** `Std.HttpServerHost` gains, on all three twins: `tryStartTask(work): Bool` (`startTask` that reports a thread that could not be created instead of panicking; always `true` on dotnet and the JVM, `false` on native when `lyric_thread_spawn_detached` fails, the retain undone, and `startTask` becomes `tryStartTask` plus the panic); `ensureThreadCapacity(connections)` (was zero-argument); `defaultMaxConnections()` (1000 on dotnet and native, 10000 on the JVM, D780 decision 9); and `AcceptOutcome` with `acceptOutcome(e: TcpError)` (`AcceptStop`, `AcceptRetry`, `AcceptBackoff`), which hides that native's `AcceptFailed` carries a classification and the other two targets' does not. `Std.TcpHost` gains `hostCloseListener` on dotnet and the JVM as a documented no-op: native keeps the listening descriptor open after `hostStopListener` and frees it there, so the driver calls it once its accept loop has ended.
3. **One task per connection, not `WorkerSet`.** The driver starts each connection task with `tryStartTask` and counts tasks itself. `WorkerSet` was not used: it posts a completion credit per task started and keeps it until a join, so a server that outlives billions of connections would overflow the dotnet `SemaphoreSlim` and, on native, grow a thread-id list without bound. The accept loop treats `tryStartTask == false` as a refused connection (close, release the permit, a 5 ms pause, keep accepting), which is the native thread-creation failure of the S2 review; on dotnet and the JVM it cannot occur, and the code path that shares it (a connection refused because the listener is stopping) is the one the tests drive.
4. **Pull queue.** `items` (a `List[HttpContext]`) under a `Mutex`, with the availability `Semaphore` posted while the lock is held (#6803). `ServerFifo[T]` (a mutex-guarded list with a head index, public only because `H2Exchange` and `H2Link` are) replaces `ConcurrentQueue` for the h2 outbox, chunk queues and inbound reads.
5. **Stop contract (D780 decision 8), the same on every target the driver will serve.** `stopListener` sets `stopping` under the lock; empties the queue; shuts down every registered connection (registration happens before the task starts, removal before the socket is closed, so a stop never touches a socket a task has begun to release, #6792, #6795); completes every request that was queued and never pulled (#6796, #6803) and every request that finishes parsing afterwards (#6798); wakes every puller; closes the listening socket (#6806); posts one extra connection permit so an accept loop parked at the cap wakes, sees the stop and closes that connection; then waits, polling at 1 to 20 ms because the seam has no timed wait, until the accept loop and every connection task (and each h2 reader) have finished, bounded by `LYRIC_HTTP_STOP_GRACE_MS` (default 5000). Only when that wait succeeded does it call `hostCloseListener` and release the TLS state. A context already handed to a caller stays the caller's obligation, so a stop issued while one is outstanding returns after the grace period. A second `stopListener` returns at once. A draining h2 connection ends when the listener is stopping instead of waiting for its watchdog.
6. **`nextContext` and `tryNextContext` (D780 decision 6).** After the stop `nextContext` panics with a message naming `tryNextContext`, which returns `None`; neither ever blocks, because each woken puller passes the wake-up on. This is a behaviour change on dotnet: a puller parked in `nextContext` on a stopped listener used to stay parked forever. `lyric-web` calls `stopListener` only on its fatal-listener path, which exits the process straight after (`Env.exitCode`), so it is unaffected; its accept loop moves to `tryNextContext` in S6.
7. **The dotnet thread-per-connection defect (D780 defects, the 10 000 idle connections case).** Cause, confirmed by measurement: each connection holds a threadpool thread blocked in a read, and `SetMinThreads(200, 200)` left every connection past the first few hundred behind the pool's one-thread-per-500-ms injection. `ensureThreadCapacity(connections)` now raises the minimum to twice the connection cap plus 64 (an h2 connection holds two threads), once per listener; raising the minimum allocates nothing. D780's B5 on the same machine: before, 0 of the trickle requests served and 8 errors in 20 s with 247 threads; after, 6498 served with 0 errors, p99 1.6 ms, 10 000 idle connections all answering afterwards, 596 MB RSS and 10 055 threads (the JVM gate for RSS is 1.5x Undertow, not meaningful for dotnet). B5 stays exempt from the S3 gate as D780 says; the defect is fixed, not merely tracked.
8. **Request bodies.** The body is gathered as a list of the engine's chunks and joined once (`ByteChunks`), replacing the BCL `List<byte>.AddRange` extern, which no other target has. A single-chunk body is not copied at all, a many-chunk body is joined in pairwise merges.
9. **Per-request completion.** `ConnHandoff` is now per request and carries `responded`, so the context's `done` is released once however many times a handler completes the exchange, and the connection task releases it after the wait. An h2 context carries one never-posted `done` per connection (`unusedDone`) instead of a semaphore per stream.
10. **Behaviour that does not change on dotnet:** h1 and h2 through the same pull surface, the h2 scheduler, rejected-stream bookkeeping, the three timeouts and their overrides, `takeConnection` and its refusals, chunked responses, the 413 body cap, the `LYRIC_HTTP_MAX_CONNECTIONS` cap (default 1000) and its backpressure, TLS handshakes off the accept loop. A failed accept on dotnet still ends the accept loop (`AcceptStop`), as before.

## What S4 and S5 inherit

The driver was also run, by hand and not wired into CI, against the JVM and native kernels' targets with `_kernel_jvm/http_server.l` and `_kernel_native/http_server.l` removed from a copy of the stdlib: `http_server_stop_tests.l` (13 cases) passes on `--target jvm` and on `--target native` (the native run failed on its first attempt, a listening socket still held after `stopListener`, which is what `hostCloseListener` fixes). That is evidence the h1 driver compiles and the stop contract holds on both, not the S4 or S5 acceptance (no h2 on either, no TLS, no benchmark gates, no ASan). What those slices still have to do:

- **S4 (JVM):** delete `_kernel_jvm/http_server.l`; `TlsListenError.message`/`InvalidConfig` and the `resolve*` helpers arrive with the shared file; run the dotnet h2 cases on the JVM (they use dotnet externs for the puller today, port them to `startTask`); the B1 to B6 gates of D780.
- **S5 (native):** delete `_kernel_native/http_server.l`; the shared file's per-listener `Mutex`, `Semaphore`s (`guard`, `available`, `connLimit`, `quiet`) and the h2 per-stream FIFOs and semaphores are never released (a no-op on dotnet and the JVM; on native they are malloc'd slots, freed in the old kernel after the puller accounting of #6802), and a context's `done` is released by the connection task only; a puller still parked at `stopListener` must keep `available` and `guard` alive (`waitingPullers`); the native `lyric_*` closure and tid lifetime is already covered by `tryStartTask`. The old native kernel's self-tests (`llvm_http_server_self_test.l`) are the acceptance, under ASan.

## Verification

dotnet, v0.7.15 compiler with the stdlib bundle rebuilt from this tree: `http_server_dotnet_tests.l` 33 of 33 (32 plus a new idle-h2 stop case), `http_server_stop_tests.l` 13 of 13 (new), `http_server_host_tests.l` 15 of 15 on dotnet, the JVM and native (3 new), the h2 curl smoke and the scheduler smoke (`dotnet-h2-smoke.sh`), `tls_tests`, `http_bytes_body_tests`, `http_async_concurrency_tests`, `http_timeout_tests`, `tcp_host_tests`, `tcp_host_tls_tests`, `http_tls_client_tests`, `tls_server_config_tests`, `http_version_tests`, and the lyric-web (102), lyric-ws (66), lyric-search (53), lyric-otel (56) and lyric-ui (119) suites on dotnet. A mutation run (the connection shutdown loop of `stopListener` removed) fails the idle keep-alive and unpulled-queue stop tests. JVM: `http_server_jvm_tests.l` (3) and `tls_server_jvm_tests.l` (8) still pass on the JDK kernel, and a program importing `Std.HttpServer` on the JVM and on native still serves through its own kernel. Benchmarks (`scripts/ci/http-server-benchmark.sh dotnet b1w b2w b3w b4h`, wrk and h2load, the same container, two runs before and three after, server and generator on one 4-core machine):

| | before (2 runs) | after (3 runs) | after against the lower before |
|---|---|---|---|
| B1 hello keep-alive, req/s | 149 244, 153 276 | 149 237, 147 817, 157 355 | 99% |
| B2 connection per request, req/s | 20 082, 19 261 | 19 402, 21 504, 19 145 | 99% |
| B3 echo 64 KiB, req/s | 7 715, 7 397 | 19 207, 19 690, 19 888 | 260% |
| B4 h2 over TLS, req/s | 50 379, 55 250 | 65 522, 56 353, 67 119 | 112% |

Every cell is at least 90% of its pre-refactor figure (the S3 gate). B3 is faster because the request body no longer goes through a per-chunk `List<byte>` copy. Differences under about 10% between single runs are noise on this machine (D780).

## Not verified

The CI scripts were edited, not run end to end. No ASan run of the native twin of the seam additions beyond the 15 seam tests (`tryStartTask`'s failure path cannot be provoked). `lyric fmt` is v0.7.15's, not the tree's. The shared file's TLS and h2 paths on the JVM and native were not run.
