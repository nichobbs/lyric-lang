# D789 - The JVM adopts the shared HTTP server driver; the JDK `com.sun.net.httpserver` kernel is deleted (docs/73 slice S4)

**Status:** accepted. Extends D788 (S3, the shared driver), D786 (S2, the seam), D780 (S0, the gates) and D621 (S1, `Std.TcpHost` fit for a server); closes docs/61 decision 6 (JVM convergence) for `Std.HttpServer`. The plan numbered this decision D616; that id was taken, so it takes the next free one. One gate is missed and recorded as such (B3 server RSS, decision 10); the 30 minute B6 soak was not run.

## Context

S3 moved the dotnet kernel into one Lyric file, `lyric-stdlib/std/_kernel/http_server.l`, with no extern, over `Std.HttpEngine`, `Std.TcpHost` and the `Std.HttpServerHost` seam. The JVM loader shadowed it with `_kernel_jvm/http_server.l`, a 676-line kernel over `com.sun.net.httpserver.HttpServer`: HTTP/1.1 only, no h2, no mTLS (#5930), no `takeConnection`, no limits or `resolve*` helpers, a fixed 10 MiB body cap, headers renormalised by the JDK, and a `HttpContext` that was an alias of the JDK's `HttpExchange`. S0 measured it (D780): as shipped it stalls every keep-alive response about 44 ms behind Nagle. The experiment recorded in D788 had already run the stop suite through the shared driver on the JVM with that kernel removed.

## Decision

1. **Delete `_kernel_jvm/http_server.l`.** The JVM loader then reads the shared file. Nothing was added to the shared file for the JVM that is not also correct on dotnet: `TlsListenError` and its `.message`, `InvalidConfig`, `tryNextContext`, `startListener{,Tls}WithLimits`, the `resolve*` helpers, `takeConnection` and the h2 scheduler all arrived with S3, and the JVM seam (`_kernel_jvm/http_server_host.l`, S2) and `Std.TcpHost` (S1) already carried what the driver needs, including server ALPN `h2` then `http/1.1` and `setNeedClientAuth`/`setWantClientAuth` through `Std.TlsServerContext`. The record-arity limit of the JVM backend (#6089) was not hit anywhere in the driver: it compiles and runs unchanged. The JVM connection cap default stays 10 000 (`defaultMaxConnections`, D780 decision 9).
2. **Behaviour changes on the JVM, all intended.** `Std.HttpServer` serves HTTP/2 over ALPN; `startListenerTls` supports mTLS (`requireClientCert`/`clientCa`) and returns `InvalidConfig` for `requireClientCert` without `clientCa` (the old kernel returned `NotSupportedOnTarget` for any mTLS request); `takeConnection` works (S7b needs it); `startListener{,Tls}WithLimits` and the `resolve*` helpers exist; the body cap is the engine's `EngineLimits.maxBodyBytes`, so it is configurable; `stopListener` shuts connections down and waits (D788 decision 5); request header names keep the client's capitalisation (the JDK server rewrote `X-Tag` to `X-tag`); `HttpContext` and `HttpListener` are Lyric records, not JDK types, so code that called `HttpExchange` methods on a context breaks (none in this repository or in `lyric-ecosystem`). A TLS handshake that times out can send the peer a TLS alert record before the close on the JVM (JSSE), where dotnet closes silently; the shared test accepts an alert and nothing else before EOF.
3. **`Std.HttpServer` no longer re-exports `Std.TlsServerContext`.** The old kernel did (`pub use`) so that `lyric-web`'s Undertow kernel could reach `serverSslContextFromConfig[Mtls]`. That kernel now imports `Std.TlsServerContext` directly (S6 deletes the use), and so do `tls_server_jvm_tests.l` and the TIR builder-shape script that depended on the re-export.
4. **Failure to start a task.** The JVM seam's `tryStartTask` now catches the `Error` that `Thread.startVirtualThread` throws when the JVM is out of memory or native threads and returns `false`; the shared accept loop turns `false` into one refused connection (close, release the permit, a 5 ms pause, keep accepting, D788 decision 3), and `startTask` panics. The failure cannot be provoked here, so it is covered by reading, not by a test (the S2/S3 reviewers' note).
5. **S3 regression fixed: `HttpListener` is `@sendable` again.** S3 changed `HttpListener` from a record over `@sendable` host types into a `ref record` with `var` fields, which made `spawn serve(listener)` a T0225 error (D404) on every target: the JVM compiler self-tests `stdlib_jvm_kernels_self_test.l` and `http_version_jvm_self_test.l` stopped compiling, and dotnet had the same break. The listener's mutable state is touched only under its `guard` mutex, so the record carries `@sendable` with an `@axiom` saying so (D404 decision 2); docs/17 gets the one `Std.HttpServer` row back in the .NET table (the file lives in `_kernel/`), 43 .NET and 33 JVM axiom files. This is the only edit to the semantic content of the shared file besides decision 6; it is an annotation.
6. **Two allocation reductions in the shared file, found by the B3 profile.** On the JVM a `slice[Byte]` is a boxed array and a slice taken out of a `List[slice[Byte]]` is converted back to its element type, which copies it. `ByteChunks` now holds the first chunk outside its list (a one-chunk body is returned as it is) and `respondBytesWith` writes a body of 16 KiB or more as its own transport call after the head instead of `head.concat(body)`, which the transport's write window then split again. Both are neutral or better on dotnet (D788 table, re-measured below). `Std.TcpHost` on the JVM grows a connection's read buffer from 16 KiB to 64 KiB the first time a read fills it, so a bulk body arrives in fewer chunks while 10 000 idle connections still hold 16 KiB each (B5 below). JFR allocation per 64 KiB echo request fell from 2.06 MB to 1.1 MB (Undertow: 0.52 MB).
7. **Tests.** `http_server_dotnet_tests.l` becomes `http_server_tests.l`, target neutral: its background threads come from `startTask` and `Semaphore` (it declares no extern), its collection helper is a mutex-guarded list, and it runs on dotnet and the JVM with 35 cases (33, plus the 10 MiB cap answered `413` and never dispatched, and a chunked h1 response, both carried over from the retired `http_server_jvm_tests.l`). Three cases changed meaning rather than syntax: the connection-cap resolver test compares with `defaultMaxConnections()` (1000 and 10 000), the silent-TLS-peer test allows a TLS alert before EOF, and `val body: String` is annotated where a `match await` result is bound (a JVM inference limit the existing `tcp_host_tls_tests.l` already works around). `tls_server_jvm_tests.l` keeps its raw-JDK-client cases (6) and drops the two cases that asserted the old `NotSupportedOnTarget` rejection; `tls_tests.l` no longer tolerates an "unsupported" mTLS outcome. `dotnet_h2_smoke.l` and its two scripts become `h2_smoke.l`, `h2-smoke.sh <dotnet|jvm>` and `h2-scheduler-smoke.sh`; `stdlib-net-tests.sh jvm` runs the neutral suite, the stop suite and the curl `--http2` smoke. `http_server_jvm_tests.l` is deleted, its cases ported.
8. **Removed as dead.** `_kernel_jvm/http_server.l` and its `@axiom` row (docs/17), the `jvm-nodelay` target of `http-server-benchmark.sh` (it existed for the JDK server's Nagle default), the JVM `HttpsServer` references in docs/61, docs/44 and the kernel READMEs, and the `Std.HttpServer` JVM section of `lyric-stdlib/std/_kernel_jvm/README.md`. `lyric-web`'s Undertow kernel and `Ws.Kernel.Jvm` stay (S6, S7b).
9. **Q5 (push dispatch) is decided: not added.** B1 on the shared driver is 150% of Undertow through the pull hop and B3's miss is allocation, not dispatch (JFR: no frame of the queue or semaphore is in the top allocators or the profile).
10. **B3 server RSS misses its gate, and the gate stays as D780 wrote it.** See the table. The cause is the JVM's `slice[Byte]` representation, not the driver's structure: a 64 KiB body costs a boxed array of 256 KiB per copy, the request path makes four copies (socket read, the engine's body slice, the chunk join, the write), and G1 sizes the young generation to the allocation rate (1.5 GB heap against Undertow's 0.7 GB; with `-Xmx768m` the same server holds RSS at 799 MB and 3 831 req/s, 98% of the default). Throughput and p99 pass. The fix is representing `slice[Byte]` as `byte[]` in the JVM backend (nichobbs/lyric-lang#9245, the same item D621 recorded for the transport), which removes the boxing and the conversions and brings the request path to Undertow's allocation; the issue text is in the progress note. The slice is accepted with this gate open because every other gate passes with margin, the figure is bounded by the heap ergonomics and not by the live set (90 MB), and the alternative, keeping the JDK kernel, was already rejected by D780 (it cannot do h2, mTLS or `takeConnection`).

## What S5 inherits

The shared file now carries `@sendable`/`@axiom` on `HttpListener`, the `ByteChunks` change and the split head and body write; native keeps its own kernel until S5 deletes it, and the native `HttpListener` already has its own `@sendable`. The shared file moves to `lyric-stdlib/std/http_server.l` in S5 (D780). `lyric-web` moves off Undertow in S6; `Web.addWebSocket` over `takeConnection` on the JVM is S7b.
