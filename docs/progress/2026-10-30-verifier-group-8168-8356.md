# Verifier: Result/Option patterns, `??`, aliases, record method results (#8168, #8356, #8218, #8245)

## `Result` and `Option` patterns, `??`, aliases (#8168)

These forms used to fail closed (V0027 on the arm, V0023 on the operator).

- `case Ok(p)`, `case Err(p)`, `case Some(p)` over the standard `Result` or
  `Option` match where the case test holds and the payload matches `p`; the
  payload bindings are the datatype's selectors, so a `requires:` about
  `r.value` reaches the binding. `case None` is `not isSome`. A nested
  payload pattern (`Some(0)`) is part of the arm's condition.
- Unguarded arms that cover both cases end the match: no V0029 warning, and
  the match's value does not depend on an unreachable fallthrough.
- `a ?? b` on an `Option` (or `T?`) is `isSome(a) ? value(a) : b`; `b`'s side
  conditions and facts hold under `not isSome(a)` only.
- A non-generic `alias` of `Result[T, E]`, `Option[T]` or `T?` has the
  datatype's sort. A generic alias is not expanded yet and stays an
  uninterpreted sort (fails closed).
- A union or record the file declares named `Result`/`Option` (or one it may
  import from outside `Std.*`) keeps its own sort and its patterns stay
  unmodelled; the modelling is driven by the sort, never the bare name.

Tests: `verifier_self_test.l`, "match patterns on Result and Option ...",
"?? on an Option ...", "an alias of Result or Option ...", "a union named
Result is the user's own ...".

## Methods of a generic record return the instance's sort (#8356)

A call `b.getV()` of a record-body method on a non-`self` receiver was an
uninterpreted application whose result had the shared "unmodelled" sort, so
it could not be compared with an `Int` (V0033). The declared result sort of
each record method is now recorded in the record's sort parameters and
instantiated at the receiver's sort (`Box[Int]` gives `Int`). The method's
contract and `@pure` body are still not applied at such a call (record-body
methods are not callees); that is the remaining part of #8356.

## Slice `==` (#8218)

The verifier half was already on main (`slice ==` fails closed, `array ==`
compares elements). The language reference now states that `==` on slices is
by reference on dotnet. The codegen half is not fixed here: a bare
`[1, 2]` is typed `slice[Int]`, not an array, so `[1, 2].toSlice()` calls an
unknown member on a slice (the checker records no type for it, T0120 later on
dotnet and J008 on the JVM). It needs the checker to type a bracket-literal
receiver of `.toSlice()` as `array[N, T]`, which touches the array-site
bookkeeping in `Lyric.ContractElaborator.ArrayOps`.

## Package membership (#8245)

Already fixed by #8227: `lyric prove` runs the build's checks first, so a
file the build rejects (B0013) is reported as such and nothing is proved;
`scripts/ci/prove-package-scope.sh` asserts it for `otherpkg`.
